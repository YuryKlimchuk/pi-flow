# Design

## Context

Production-контур GitHub собирается последовательно changes 1–5. Этот change проверяет его через три уровня: публичный контракт, локальный HTTP-адаптер и архитектура модульного монолита.

## Goals / Non-Goals

**Goals:** детерминированные тесты без реального GitHub, проверка заголовков/пагинации/distinction/idempotency, архитектурные правила, compile/test/OpenSpec gates. **Non-Goals:** новые GitHub endpoint или бизнес-функции.

## Decisions

### D1: Пирамида тестов
**Решение:** contract-тесты отделить от интеграционных тестов адаптера. **Почему:** ошибки публичной семантики и HTTP-мэппинга локализуются. **Альтернатива:** только end-to-end — медленно и не диагностично.

### D2: Локальный mock HTTP server
**Решение:** поднимать локальный сервер с контролируемыми ответами и проверкой запросов. **Почему:** проверяются реальные заголовки, query, Link и последовательность GET/POST без сети. **Альтернатива:** mock RestClient — не проверяет HTTP wiring.

### D3: Архитектурные gates
**Решение:** сохранить `ApplicationModules.verify()` и добавить направленные правила для `web → workflow → ...` и запрета инфраструктурного импорта. **Почему:** Spring Modulith проверяет границы, ArchUnit делает направление явным. **Альтернатива:** ручной review — неавтоматизируем.

### D4: Финальный порядок проверок
**Решение:** сначала compile, затем test, затем validate каждого change и финально текущего testing change. **Почему:** быстрые структурные ошибки выявляются раньше.

## Risks / Trade-offs

- Mock server может не воспроизвести все особенности GitHub; тесты покрывают зафиксированные observable-контракты, а не внешний сервис целиком.
- Архитектурные правила могут быть хрупкими при переименовании пакетов; это компенсируется явными правилами и документацией ответственности модулей.

## Open Questions

- Нужен ли отдельный профиль для длительных интеграционных тестов; на текущем scope локальные тесты должны выполняться обычной командой `./mvnw -q test`.
