# Design

## Context

Подключение, авторизация и общий page-механизм подготовлены предыдущими changes; этот change реализует REST операции Issues.

## Goals / Non-Goals

**Goals:** список, фильтры, пагинация, distinction Issue/PR, детали и ошибки. **Non-Goals:** создание PR и локальная работа с ветками.

## Decisions

### D1: GitHub Issues endpoint
**Решение:** использовать `GET /repos/{owner}/{repo}/issues` и endpoint деталей. **Почему:** API возвращает и Issues, и PR с явным `pull_request`. **Альтернатива:** отдельный endpoint pulls — не даёт единую ленту Issues.

### D2: Явный признак Pull Request
**Решение:** маппить наличие `pull_request` в `pullRequest`. **Почему:** номер и URL сами по себе недостаточны. **Альтернатива:** угадывать по URL — хрупко.

### D3: Единая пагинация
**Решение:** использовать page/perPage и Link fallback из репозиториев. **Почему:** одинаковый потребительский контракт. **Альтернатива:** скрытая загрузка всех страниц.

### D4: 404 как not found
**Решение:** не создавать частичный объект. **Почему:** отсутствие Issue — бизнес-результат, а не пустой список.

## Risks / Trade-offs

- GitHub объединяет Issues и PR в endpoint; признак должен проверяться на каждом элементе.
- Описание может быть null; публичная модель должна явно отражать отсутствие описания.

## Open Questions

- Нужна ли отдельная фильтрация `state`; текущий контракт передаёт поддерживаемые GitHub query-фильтры.
