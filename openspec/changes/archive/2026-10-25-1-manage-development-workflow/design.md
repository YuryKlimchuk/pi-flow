# Design

## Context

См. `proposal.md` — Why. Ограничения, которые формируют подход: Java + Spring Boot, модульный монолит (DDD, Spring Modulith), Temporal как движок долговременного выполнения workflow, Pi Coding Agent для ролей Analyst/Architect/Developer/Reviewer, Git/GitHub для артефактов и PR, web-интерфейс для запуска и взаимодействия с пользователем.

Требования поведения (что именно делает процесс) описаны в `specs/development-workflow/spec.md`.

## Goals / Non-Goals

**Goals:**
- Подготовить наглядную Mermaid-диаграмму сквозного workflow, описывающую этапы, состояния, переходы, контрольные точки, циклы исправлений, обработку ошибок и управление блокировкой.
- Согласовать, как диаграмма отражает решения из spec (лимит 3, терминальность `FAILED`/`CANCELLED`, удержание блокировки).

**Non-Goals:**
- Не пишется программный код и не строится внутренняя архитектура приложения.
- Не вводятся новые модули/сущности.
- Не фиксируется распределение этапов между доменной моделью и application-слоем с Temporal.
- Не входит проверка, одобрение и слияние PR.

## Decisions

### D1: Диаграмма описывает последовательность этапов поверх общих состояний

Диаграмма показывает шесть этапов (`PREPARING_REPOSITORY`, `ANALYZING_REQUIREMENTS`, `DESIGNING_SOLUTION`, `IMPLEMENTING`, `REVIEWING`, `FINALIZING`) и общие состояния (`RUNNING`, `WAITING_FOR_USER`, `PAUSED`, `COMPLETED`, `FAILED`, `CANCELLED`), а также переходы между ними.

- **Почему**: это минимальный наглядный каркас, достаточный для согласования процесса без кода.
- **Альтернатива**: словесный список без схемы — отброшено, так как теряется наглядность переходов и циклов.

### D2: Переходы между этапами описываются условиями, а не жёсткой машиной состояний в коде

Переход между этапами определяется результатом предыдущего этапа и подтверждением пользователя; это фиксируется на уровне требований, а не привязывается к конкретной реализации.

- **Почему**: поведение должно быть проверяемым, но способ реализации остаётся открытым (Temporal или иначе).
- **Альтернатива**: жёсткая машина состояний — отложена до уточнения распределения с Temporal.

### D3: Блокировка репозитория управляется явно и освобождается в терминальных состояниях

Блокировка берётся на подготовке, удерживается в ходе процесса и гарантированно освобождается при `COMPLETED`, `FAILED` и `CANCELLED`.

- **Почему**: исключить параллельные конфликтующие workflow; гарантия освобождения — обязательное требование.
- **Решение (согласовано)**: блокировка удерживается и в `WAITING_FOR_USER`, и в `PAUSED` — чтобы исключить параллельный запуск конфликтующего workflow, пока текущий процесс не завершён. Освобождение происходит только в терминальных состояниях `COMPLETED`/`FAILED`/`CANCELLED`.

### D4: Состояние и история отражаются в диаграмме как сведения для восстановления

Диаграмма показывает, что журнал хранит текущее состояние, пройденные этапы, контрольные точки и артефакты — достаточное для восстановления и отображения процесса.

- **Почему**: это часть согласованного поведения; на диаграмме фиксируется, что восстановление не повторяет завершённые этапы.
- **Альтернатива**: не показывать сохранение состояния — отброшено, так как без него не ясно, как процесс возобновляется.

### D5: Классификация ошибок — повторяемые против фатальных

- **Повторяемые** (допускают retry с лимитом): ошибки сборки, тестов, замечания ревью — устраняются повторной итерацией внутри этапа.
- **Фатальные** (переводят в `FAILED`): недоступность Git/GitHub, потеря блокировки репозитория, нарушение целостности состояния.

### D6: Лимиты циклов исправлений и критерий приемлемости ревью

- Лимит итераций исправлений в `DESIGNING_SOLUTION` и `REVIEWING` — **3**; при превышении процесс переходит в `FAILED` (или `WAITING_FOR_USER` для смены решения).
- Приемлемый результат ревью — отсутствие блокирующих замечаний; некритичные замечания не блокируют переход.

### D7: Возобновление процесса

- После `PAUSED` и `WAITING_FOR_USER` — возобновление с текущего этапа (завершённые этапы не повторяются).
- `FAILED` и `CANCELLED` — терминальны; возобновление невозможно, только новый запуск workflow.

### D8: Ошибка на `FINALIZING`

- Если PR уже создан, но уведомление или освобождение блокировки не удалось — процесс переводится в `FAILED`, при этом система всё равно пытается освободить блокировку (best-effort), чтобы не оставить репозиторий заблокированным.
- Повторный запрос создания PR при уже существующем PR не создаёт дубликат — используется существующий.

### D9: Обработка рабочего дерева и ветки

- Нечистое рабочее дерево: перед началом процесс требует чистого состояния либо явного разрешения пользователя на работу с указанным содержимым.
- Существующая ветка с целевым именем: используется повторно либо создаётся уникальная — решение фиксируется перед началом и не нарушает процесс.

### D11: Формат и место хранения диаграммы

Диаграмма выполняется в нотации Mermaid и сохраняется отдельным файлом в корне каталога спецификаций `openspec/specs/`.

- **Почему**: Mermaid разрешён правилом проекта для нетривиальных схем; отдельный файл — согласованное место хранения итогового артефакта.
- **Альтернатива**: встраивание диаграммы только в `design.md` — отброшено, так как диаграмма должна быть самостоятельным результатом.

## Risks / Trade-offs

### R1: Распределение ответственности с Temporal не зафиксировано

[Risk] Возможна переделка, если позднее распределение этапов между доменной моделью и Temporal изменится. → Mitigation: держим границу на уровне требований/поведения, не привязываясь к реализации.

### R2: Удержание блокировки при ожидании пользователя

[Risk] Долгое ожидание в `WAITING_FOR_USER`/`PAUSED` блокирует репозиторий. → Mitigation: принято осознанно (исключает конфликты); при необходимости в будущем добавить таймаут/эскалацию.

### R3: Лимиты циклов исправлений

[Risk] Зацикливание при недостижимом критерии. → Mitigation: лимит 3 итерации с переходом в `FAILED`/`WAITING_FOR_USER`.
