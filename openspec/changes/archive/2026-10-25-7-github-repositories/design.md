# Design

## Context

Адаптер и авторизация подготовлены `github-api-connection`; публичная модель и порт определены `github-module-contract`.

## Goals / Non-Goals

**Goals:** `/user/repos` или согласованный доступный endpoint, маппинг элементов, page/perPage, Link header, валидация и ошибки. **Non-Goals:** Issues, branch publication и PR.

## Decisions

### D1: Страничный контракт
**Решение:** возвращать элементы и `hasNext` вместе с параметрами страницы. **Почему:** потребитель управляет загрузкой. **Альтернатива:** автоматически читать все страницы — непредсказуемая нагрузка.

### D2: Link header имеет приоритет
**Решение:** использовать `rel="next"`, а при отсутствии header — размер страницы. **Почему:** GitHub явно сообщает продолжение. **Альтернатива:** только размер ответа — теряет серверную семантику.

### D3: Валидация до HTTP
**Решение:** проверять page/perPage в application-слое. **Почему:** невалидные запросы не расходуют API rate limit. **Альтернатива:** делегировать GitHub — менее определённая ошибка.

### D4: Маппинг минимальной модели
**Решение:** сохранять только id, owner, name и URL. **Почему:** соответствует публичному контракту. **Альтернатива:** экспортировать весь GitHub JSON — повышает связанность.

## Risks / Trade-offs

- При отсутствии Link header эвристика размера может не обнаружить следующую страницу ровно размера `perPage`; это ограничение fallback, а реальный GitHub обычно присылает Link.
- Endpoint `/user/repos` зависит от scope токена; authorization ошибки остаются типизированными.

## Open Questions

- Нужен ли отдельный endpoint организации; текущая операция определяется доступными пользователю репозиториями.
