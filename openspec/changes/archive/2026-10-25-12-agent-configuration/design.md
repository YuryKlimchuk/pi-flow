# Design

## Context

Публичный контракт из Change 1 должен получить воспроизводимую конфигурацию запуска. Pi запускается локально, поэтому путь к executable, argv, рабочая директория и окружение должны быть проверяемыми до создания процесса.

## Goals / Non-Goals

**Goals:** typed-конфигурация, безопасный argv, рабочая директория, allowlist окружения и диагностируемые ошибки. **Non-Goals:** создание процесса, сбор stdout/stderr, timeout и отмена.

## Decisions

### D1: Typed configuration
**Решение:** хранить executable, базовые аргументы, ограничения и имена разрешённых переменных в конфигурации модуля. **Почему:** параметры валидируются и не смешиваются с пользовательской строкой. **Альтернатива:** произвольная shell-строка — отклонена.

### D2: Список аргументов
**Решение:** передавать команду как `List<String>` для последующего `ProcessBuilder`. **Почему:** пробелы и спецсимволы не становятся shell-синтаксисом. **Альтернатива:** `sh -c` — запрещена.

### D3: Рабочая директория
**Решение:** принимать путь в команде и проверять существование, каталог и доступность. **Почему:** Pi должен работать в указанном workspace.

### D4: Окружение и секреты
**Решение:** разрешать только явно перечисленные имена переменных, маскировать значения в диагностике и не сохранять секреты в результате. **Почему:** минимизация утечки.

### D5: Недоступный Pi
**Решение:** отсутствие executable, неверный путь и отсутствие execute-доступа дают типизированную ошибку до выполнения задачи. **Альтернатива:** отложенная ошибка внутри workflow — отклонена.

## Risks / Trade-offs

- Allowlist требует явного обновления при появлении нового параметра.
- Проверка доступности до запуска подвержена race condition; окончательная ошибка запуска всё равно должна быть обработана Change 3.

## Open Questions

- CLI vs RPC окончательно фиксируется в Change 3; этот change описывает транспортонезависимую подготовку.
- Список профилей ролей уточняется в Change 4.
