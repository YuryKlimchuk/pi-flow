# Design

## Context

Change использует публичные порты и модели `github-module-contract`; адаптеру нужен синхронный HTTP-клиент для GitHub REST API.

## Goals / Non-Goals

**Goals:** RestClient, typed properties, Authorization, тайм-ауты, безопасная классификация ошибок. **Non-Goals:** бизнес-операции репозиториев, Issues и PR — они реализуются в changes 3–5.

## Decisions

### D1: Spring RestClient
**Решение:** использовать `RestClient`. **Почему:** он уже соответствует синхронному Spring-стеку и оставляет контроль endpoint/заголовков. **Альтернатива:** SDK GitHub — отклонён из-за лишних моделей и скрытой семантики.

### D2: Typed properties
**Решение:** отдельный configuration properties объект с URL, token, page size и timeout. **Почему:** внешняя конфигурация проверяема и секрет не входит в публичный контракт. **Альтернатива:** передавать токен в каждом вызове — небезопасно.

### D3: Fail-fast без токена
**Решение:** проверять токен до отправки запроса. **Почему:** исключает неавторизованный трафик. **Альтернатива:** отправлять запрос и обрабатывать 401 — скрывает ошибку настройки.

### D4: Санитизация ошибок
**Решение:** сохранять статус, операцию и безопасную причину, удалять секрет. **Почему:** потребителю нужна классификация retryable. **Альтернатива:** проброс RestClientException — транспортный контракт наружу.

## Risks / Trade-offs

- Требуется аккуратно не логировать заголовки при DEBUG; это покрывается mock HTTP-тестом и ревью конфигурации.
- Fail-fast делает локальный запуск без токена непригодным для GitHub-операций, но приложение может стартовать до первого вызова.

## Open Questions

- Следует ли делать отсутствие токена ошибкой старта приложения или первой операции; в этом change фиксируется ошибка до HTTP-вызова, без обязательного отказа старта.
