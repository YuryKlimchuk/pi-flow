# Proposal

## Why

`AgentStageRunner.promptFor(stage, workflow)` builds every prompt from only `workflow.getTargetRepo()` and `workflow.getTask()` (confirmed by reading `AgentStageRunner.promptFor`); the analysis produced by `PROJECT_ANALYSIS` and the proposal produced by `CHANGE_PROPOSAL` are discarded as free text in `StageOutcome.output()` and never passed forward, so `IMPLEMENTATION` and `REVIEW` re-derive context from scratch with no structured link to what analysis or planning actually found. User corrections are similarly lossy: `requestRevisions()` and `requestFurtherWork()` (in `WorkflowEngineImpl`) move the workflow back a stage with no field carrying *why* - the user's revision request or further-work feedback is not recorded anywhere `StageRunner`/`AgentStageRunner` can read, so a re-run of `CHANGE_PROPOSAL` or `IMPLEMENTATION` cannot act on the user's actual feedback. Separately, `REVIEW` is treated identically to every other agent stage: `WorkflowEngineImpl.advance()` branches only on `StageOutcome.success()` (a boolean), so a review that found no defects and a review that technically "ran without crashing" are indistinguishable from the engine's perspective, and there is no path for `REVIEW` to report a structured verdict (approved vs. changes-required) separate from whether the reviewer agent's process itself succeeded or crashed. Today's reviewer-output contract is also not machine-checkable: nothing specifies an exact, parseable shape for the reviewer's verdict, so any free-text heuristic ("look for a token") is ambiguous to extract and to review.

## Depends on

This change requires plan 10 (`10-enforce-workflow-transition-guards`) and plan 11 (`11-harden-pi-result-contract`) to be fully implemented first. This change's design and tasks assume `Workflow`'s terminal-immutability guard (plan 10) and the hardened `PiRunResult`/`PiJsonlParser` completion contract (plan 11) already exist in `src/main/java`; it does not re-derive, duplicate, or provide a fallback implementation of either. There is no condition under which this change's tasks proceed against an unimplemented plan 10 or 11 - if either is not yet implemented when this change is picked up for implementation, implementation of this change SHALL NOT start until it is.

## What Changes

- Add a typed stage context object that `WorkflowEngineImpl`/`StageRunner` build up and pass into each agent stage invocation, carrying: the task description, the target repo, the `PROJECT_ANALYSIS` stage's findings, the `CHANGE_PROPOSAL` stage's proposal output, and any pending user feedback (a revision request message from `requestRevisions()` or a further-work message from `requestFurtherWork()`). `AgentStageRunner` SHALL build its prompt from this typed context instead of only `workflow.getTask()`/`workflow.getTargetRepo()`.
- Add API surface for the user to supply free-text feedback when requesting revisions or further work (`requestRevisions(WorkflowId, String feedback)`, `requestFurtherWork(WorkflowId, String feedback)`), and thread that feedback through the stage context so the next `CHANGE_PROPOSAL` or `IMPLEMENTATION` run can read it. **BREAKING**: existing no-argument `requestRevisions(WorkflowId)`/`requestFurtherWork(WorkflowId)` callers must supply feedback (an empty string is accepted and treated as "no specific feedback").
- Introduce a `ReviewVerdict` type (`APPROVED`, `CHANGES_REQUIRED`) that is separate from `StageOutcome.success()`: `StageOutcome.success()` continues to mean "the stage ran to completion without a technical/process error" (process crash, agent-run failure, malformed output), while a `REVIEW` stage's outcome additionally carries a `ReviewVerdict` and a list of findings, both extracted from the reviewer agent's output under an exact, machine-checkable contract (defined below). A technically successful review process always carries a verdict; a technically failed review process (crash, timeout, malformed agent output) carries no verdict and is handled as a technical failure, not as `CHANGES_REQUIRED`.
- Define the reviewer output extraction contract exactly, so verdict parsing is deterministic and never guesses from a token substring:
  - The extraction input is the reviewer agent's entire final text (`PiRunResult.finalText()`), considered as a whole - not scanned for a keyword anywhere inside it.
  - The extraction SHALL locate exactly one fenced code block tagged `json` (a single ```` ```json ... ``` ```` block) within that text, OR, if no fenced block is present, SHALL treat the entire trimmed final text as the candidate JSON document. If more than one ```` ```json ```` fenced block is present, extraction fails (ambiguous).
  - The candidate document SHALL parse as a single JSON object (not an array, not a scalar) with exactly two required top-level keys: `verdict` (a string, exactly `"APPROVED"` or `"CHANGES_REQUIRED"`, no other value, no case-insensitive matching) and `findings` (a JSON array of strings; the array SHALL be present and SHALL be empty when the verdict is `"APPROVED"` and there is nothing to report, but its presence is still mandatory).
  - Extraction fails - and is treated as fail-closed, never as a default verdict - when: the text contains no parseable JSON object by the rule above; the JSON parses but is not an object; `verdict` is missing, not a string, or not exactly one of the two literal values; `findings` is missing or not an array of strings; more than one fenced ```` ```json ```` block is present; or any JSON parse error occurs. Extraction SHALL NOT fall back to scanning the raw text for a substring like `APPROVED` when structured parsing fails.
  - A successful extraction yields exactly one `ReviewVerdict` and exactly one findings list; both are taken only from the parsed JSON object, never guessed or supplemented from surrounding prose.
- `WorkflowEngineImpl.advance()`'s `REVIEW` branch SHALL route on the verdict, not solely on `StageOutcome.success()`: `APPROVED` advances to `ACCEPTANCE`; `CHANGES_REQUIRED` returns to `IMPLEMENTATION` (as today); a technical failure (`StageOutcome.success() == false`) or a failed extraction on an otherwise-successful stage SHALL mark the workflow `FAILED` and SHALL NOT be treated as `CHANGES_REQUIRED` or `APPROVED` - failing closed so a reviewer agent that returns an unparseable or ambiguous result cannot be silently routed as if it approved or requested changes.
- The automated verification stage (`VERIFICATION`) and its boolean-pass/fail contract from `Verifier.verify()` are explicitly out of scope for this change; plan 13 owns replacing it with a configurable deterministic check and a richer pass/fail/not-configured result that this change's engine routing must remain compatible with. This change does not alter `Verifier`'s signature or the `VERIFICATION` branch of `advance()`.
- Deciding and enforcing the exact change the `IMPLEMENTATION` stage is bound to (i.e., preventing scope drift from what was approved) is explicitly out of scope for this change and is owned by a future plan (plan 14); this change only ensures the approved proposal and any user feedback are available in the stage context for that future binding logic to consume.

## Capabilities

### New Capabilities
- `stage-context-propagation`: defines the typed context (task, target repo, prior stage findings, pending user feedback) that the orchestrator builds and passes into each agent stage invocation, and how user revision/further-work feedback is captured and carried forward.
- `review-verdict`: defines the `ReviewVerdict`/findings produced by a technically successful `REVIEW` stage, the exact structured-JSON extraction contract used to obtain them, how they are distinguished from `StageOutcome.success()`, and the fail-closed handling of a technical failure or a failed extraction.

### Modified Capabilities
- `workflow-orchestration`: the `REVIEW` routing in "Correction loop" and "Final acceptance" now routes on `ReviewVerdict` rather than `StageOutcome.success()` alone, and `requestRevisions`/`requestFurtherWork` gain a feedback parameter that is persisted and threaded into subsequent stage context.

## Impact

- `src/main/java/.../workflow/api/StageOutcome.java`: gains a way to carry an optional `ReviewVerdict` and an optional findings list for `REVIEW`-stage outcomes (decided in design.md: new fields vs. a `REVIEW`-specific subtype).
- `src/main/java/.../workflow/api/WorkflowEngine.java`: `requestRevisions`/`requestFurtherWork` signatures gain a `String feedback` parameter. **BREAKING** for existing callers, including `FlowCommands`.
- `src/main/java/.../workflow/domain/Workflow.java`: gains storage for the typed stage context (prior findings, pending feedback) so it survives across `advance()` calls and persistence round-trips.
- `src/main/java/.../workflow/application/WorkflowEngineImpl.java`: builds/updates the stage context on each transition; `REVIEW` branch of `advance()` routes on `ReviewVerdict` with fail-closed handling for technical failure or a failed extraction.
- `src/main/java/.../workflow/infrastructure/AgentStageRunner.java`: `promptFor(...)` reads from the typed stage context instead of only `workflow.getTask()`/`getTargetRepo()`; the `REVIEW` case instructs the reviewer agent to emit the structured ```` ```json ```` verdict object and extracts it under the exact contract above, treating any extraction failure as a technical failure (`StageOutcome.success() == false`), never as `CHANGES_REQUIRED`.
- `src/main/java/.../shell/FlowCommands.java`: revision/further-work shell commands gain a feedback argument.
- Tests: `WorkflowEngineImplTest`, `WorkflowTest`, `AgentStageRunnerTest` gain cases for context propagation, feedback threading, verdict routing, and fail-closed extraction-failure handling.
- No changes to `agent-invocation` capability, `PiRunner`/`PiRunResult` shapes, or the `VERIFICATION` stage's `Verifier` port in this change.
