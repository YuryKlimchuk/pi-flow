# Spec Delta

## Purpose

Предоставляет наглядную диаграмму сквозного процесса разработки ПО от подготовки репозитория до создания Pull Request с участием Pi Coding Agent и пользователя в контрольных точках.

## ADDED Requirements

### Requirement: Диаграмма процесса

Результатом изменения SHALL являться диаграмма workflow (в формате Mermaid), размещённая отдельным файлом в корне каталога спецификаций `openspec/specs/`; реализация кода в рамках этого изменения НЕ выполняется.

#### Scenario: Диаграмма подготовлена

- **WHEN** изменение завершено
- **THEN** файл диаграммы существует в `openspec/specs/` и отображает этапы, состояния, переходы и контрольные точки process

#### Scenario: Отсутствие кода

- **WHEN** выполняется данное изменение
- **THEN** программный код приложения не создаётся и не изменяется

### Requirement: Workflow проходит задачу разработки от подготовки репозитория до создания Pull Request

Система SHALL проводить задачу разработки ПО через последовательность этапов: подготовка репозитория (`PREPARING_REPOSITORY`), анализ требований (`ANALYZING_REQUIREMENTS`), проектирование решения (`DESIGNING_SOLUTION`), реализация (`IMPLEMENTING`), ревью (`REVIEWING`) и завершение (`FINALIZING`).

#### Scenario: Успешное прохождение всех этапов

- **WHEN** задача разработки проходит все этапы без ошибок и подтверждена пользователем
- **THEN** система публикует рабочую ветку, создаёт Pull Request и переводит workflow в `COMPLETED`

#### Scenario: Конечная точка workflow

- **WHEN** Pull Request создан
- **THEN** workflow завершается, а проверка, одобрение и слияние PR выполняются вне текущего процесса

### Requirement: Workflow имеет предопределённые общие состояния

Система SHALL поддерживать общие состояния workflow: `RUNNING`, `WAITING_FOR_USER`, `PAUSED`, `COMPLETED`, `FAILED` и `CANCELLED`.

#### Scenario: Отображение корректного состояния

- **WHEN** процесса находится в любом из допустимых состояний
- **THEN** система отображает это состояние и позволяет отличить его от остальных

### Requirement: Подготовка репозитория

На этапе `PREPARING_REPOSITORY` система SHALL проверить репозиторий, подготовить рабочее окружение, получить блокировку репозитория и подготовить рабочую ветку.

#### Scenario: Блокировка репозитория получена

- **WHEN** запускается workflow и репозиторий готов
- **THEN** система получает блокировку репозитория, исключая параллельное выполнение конфликтующих workflow

#### Scenario: Репозиторий занят

- **WHEN** блокировка репозитория уже удерживается другим workflow
- **THEN** система не начинает выполнение и сообщает о невозможности получить блокировку

### Requirement: Анализ требований

На этапе `ANALYZING_REQUIREMENTS` система SHALL запустить Pi-агента в роли Analyst с переданной задачей и контекстом, при необходимости запросить у пользователя дополнительные сведения, сформировать требования, дождаться подтверждения пользователя и сохранить утверждённые требования в Git.

#### Scenario: Требования утверждены

- **WHEN** Analyst сформировал требования и пользователь подтвердил их
- **THEN** система сохраняет утверждённые требования в Git и переходит к следующему этапу

#### Scenario: Требуются дополнительные сведения

- **WHEN** для анализа не хватает входных данных
- **THEN** система запрашивает у пользователя дополнительные сведения и переходит в `WAITING_FOR_USER`

### Requirement: Проектирование решения

На этапе `DESIGNING_SOLUTION` система SHALL запустить Pi-агента в роли Architect, подготовить OpenSpec Proposal со спецификациями, дизайном и планом реализации, предоставить результат пользователю на проверку и повторять подготовку/проверку до утверждения, после чего сохранить утверждённые артефакты в Git.

#### Scenario: Решение утверждено

- **WHEN** Architect подготовил артефакты и пользователь утвердил их
- **THEN** система сохраняет утверждённые артефакты в Git и переходит к реализации

#### Scenario: Есть замечания к решению

- **WHEN** пользователь отклоняет результат проектирования с замечаниями
- **THEN** система повторяет подготовку и проверку до их устранения и утверждения

### Requirement: Реализация

На этапе `IMPLEMENTING` система SHALL запустить Pi-агента в роли Developer для реализации утверждённого решения, выполнить сборку и тесты, а при обнаружении ошибок исправлять их и повторять проверки, при необходимости запрашивая у пользователя дополнительные сведения.

#### Scenario: Сборка и тесты пройдены

- **WHEN** реализация выполнена и сборка с тестами проходят без ошибок
- **THEN** система переходит к этапу ревью

#### Scenario: Обнаружены ошибки реализации

- **WHEN** сборка или тесты выявляют ошибки
- **THEN** система исправляет ошибки и повторяет проверки до их устранения

### Requirement: Ревью

На этапе `REVIEWING` система SHALL запустить независимого Pi-агента в роли Reviewer, возвращать работу Developer на исправление при наличии замечаний, повторно выполнять проверки и ревью после исправлений, и повторять цикл до приемлемого результата либо приостановки процесса.

#### Scenario: Ревью пройдено

- **WHEN** Reviewer не выявил блокирующих замечаний
- **THEN** система переходит к завершению

#### Scenario: Замечания от ревью

- **WHEN** Reviewer вернул работу на исправление
- **THEN** система передаёт результат Developer, после исправлений повторяет проверки и ревью

### Requirement: Завершение

На этапе `FINALIZING` система SHALL подготовить итоговый отчёт, опубликовать рабочую ветку в GitHub, создать Pull Request, уведомить пользователя о результате, освободить блокировку репозитория и перевести workflow в `COMPLETED`. Повторный запрос создания PR при уже существующем PR SHALL не создавать дубликат.

#### Scenario: Успешное завершение

- **WHEN** Pull Request создан и уведомление отправлено
- **THEN** система освобождает блокировку репозитория и переводит workflow в `COMPLETED`

#### Scenario: Ошибка после создания PR

- **WHEN** PR уже создан, но уведомление или освобождение блокировки завершилось ошибкой
- **THEN** система переводит workflow в `FAILED` и выполняет best-effort освобождение блокировки

#### Scenario: Повторный запрос создания PR

- **WHEN** запрашивается создание PR, но PR уже существует
- **THEN** система использует существующий PR и не создаёт дубликат

### Requirement: Обработка ошибок

Система SHALL классифицировать ошибки как повторяемые (устраняемые повторной итерацией внутри этапа) или фатальные (недоступность Git/GitHub, потеря блокировки репозитория, нарушение целостности состояния). Фатальная ошибка SHALL переводить workflow в `FAILED` с сохранением причины.

#### Scenario: Повторяемая ошибка

- **WHEN** сборка или тесты выявляют устранимую ошибку
- **THEN** система исправляет ошибку и повторяет проверки, не переводя процесс в `FAILED`

#### Scenario: Фатальная ошибка

- **WHEN** возникает недоступность Git/GitHub, потеря блокировки или нарушение целостности состояния
- **THEN** система переводит workflow в `FAILED` и сохраняет причину

#### Scenario: Ожидание пользователя

- **WHEN** процесс требует ответа, решения или подтверждения пользователя
- **THEN** система переводит workflow в `WAITING_FOR_USER`

### Requirement: Лимиты циклов исправлений

Система SHALL ограничивать число итераций исправлений в этапах `DESIGNING_SOLUTION` и `REVIEWING` значением 3; при превышении лимита процесс SHALL переходить в `FAILED` или `WAITING_FOR_USER`. Приемлемым результатом ревью SHALL считаться отсутствие блокирующих замечаний.

#### Scenario: Превышение лимита итераций

- **WHEN** после трёх итераций исправлений критерий приемлемости не достигнут
- **THEN** система переводит workflow в `FAILED` или `WAITING_FOR_USER`

#### Scenario: Некритичные замечания не блокируют

- **WHEN** Reviewer выявил только некритичные замечания
- **THEN** система считает результат приемлемым и переходит к завершению

### Requirement: Возобновление, приостановка и отмена

Система SHALL допускать переход workflow в `PAUSED` и `CANCELLED`, а также возобновление из состояний `PAUSED` и `WAITING_FOR_USER` с текущего этапа без повторного прохождения завершённых этапов. Состояния `FAILED` и `CANCELLED` SHALL быть терминальными и возобновлению не подлежат.

#### Scenario: Приостановка

- **WHEN** процесс приостанавливается
- **THEN** система переводит workflow в `PAUSED` и допускает последующее возобновление

#### Scenario: Возобновление с текущего этапа

- **WHEN** workflow возобновляется из `PAUSED` или `WAITING_FOR_USER`
- **THEN** система продолжает с текущего этапа, не повторяя завершённые

#### Scenario: Отмена

- **WHEN** процесс отменяется
- **THEN** система переводит workflow в `CANCELLED` и освобождает блокировку репозитория

#### Scenario: Отказ от возобновления терминальных состояний

- **WHEN** workflow находится в `FAILED` или `CANCELLED`
- **THEN** система не возобновляет процесс; доступен только новый запуск

### Requirement: Управление блокировкой репозитория

Система SHALL удерживать блокировку репозитория на протяжении выполнения workflow, включая состояния `WAITING_FOR_USER` и `PAUSED`, и освобождать её только при завершении в состоянии `COMPLETED`, `FAILED` или `CANCELLED`.

#### Scenario: Блокировка удерживается при ожидании пользователя

- **WHEN** workflow находится в `WAITING_FOR_USER` или `PAUSED`
- **THEN** система продолжает удерживать блокировку репозитория

#### Scenario: Освобождение блокировки при завершении

- **WHEN** workflow завершается в любом из терминальных состояний
- **THEN** система освобождает блокировку репозитория

### Requirement: Сохранение состояния и истории

Система SHALL сохранять состояние и историю выполнения, достаточные для восстановления процесса и отображения его текущего состояния.

#### Scenario: Восстановление после остановки

- **WHEN** процесс останавливается и возобновляется
- **THEN** система восстанавливает процесс на основе сохранённого состояния и истории без повторного прохождения завершённых этапов
