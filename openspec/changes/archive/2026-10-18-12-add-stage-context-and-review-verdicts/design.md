# Design

## Context

See proposal.md - Why for the lost-context and undifferentiated-review-outcome gaps, and proposal.md - Depends on for the required implementation order. Current state, read from `AgentStageRunner`, `WorkflowEngineImpl`, `Workflow`, `StageOutcome`, and `WorkflowEngine`:

- `AgentStageRunner.promptFor(stage, workflow)` builds every prompt from only `workflow.getTargetRepo()` and `workflow.getTask()`; `StageOutcome.output()` (the prior stage's free text) is never read back by a later stage.
- `Workflow` stores `outcomes` as an append-only `List<StageOutcome>` with no other mutable state besides `currentStage`/`status`; there is no field for "pending user feedback."
- `WorkflowEngine.requestRevisions(WorkflowId)` / `requestFurtherWork(WorkflowId)` take no feedback parameter; `WorkflowEngineImpl`'s implementations only call `workflow.moveTo(...)` + `markInProgress()` + `advance(...)`.
- `WorkflowEngineImpl.advance()`'s `REVIEW` case is folded into the same `switch` arm as `PROJECT_ANALYSIS, CHANGE_PROPOSAL, IMPLEMENTATION, REVIEW`: it calls `stageRunner.run(stage, workflow)` and branches only on `outcome.success()` - `true` advances via `next(stage)` (to `ACCEPTANCE`), `false` loops to `IMPLEMENTATION`. There is no verdict concept; a review that "ran fine but found defects" and a review that "ran fine and found nothing" are both just `success() == true` today, so there is currently no `CHANGES_REQUIRED` signal distinct from a crash.
- `StageOutcome` is a 3-field record (`stage`, `success`, `output`); nothing optional/structured is attached today.
- `AgentStageRunner.run()` maps a `PiRunResult` directly to a `StageOutcome` via `result.status() == PiRunStatus.SUCCESS`; the reviewer agent's actual judgment, if any, is only present as free text inside `result.finalText()`.
- This design is written against plan 10 and plan 11 already being implemented: `Workflow`'s stage/status guard (plan 10's `requireAwaitingUserAt`) and the hardened `PiRunResult`/`hasRecognizedCompletion()` contract (plan 11) are assumed present and are reused, not redesigned, by this change. No task in this change re-implements either.

## Goals / Non-Goals

**Goals:**
- Give every agent stage invocation a typed context carrying task, target repo, prior `PROJECT_ANALYSIS`/`CHANGE_PROPOSAL` outputs, and any pending user feedback.
- Let the user attach free-text feedback to a revision or further-work request, and ensure that feedback reaches exactly the next relevant stage run, then is cleared.
- Separate "did the REVIEW stage execute without a technical error" from "what did the reviewer conclude," via a `ReviewVerdict` enum extracted under an exact, machine-checkable JSON contract, and route `advance()`'s `REVIEW` case on the verdict.
- Fail closed on any ambiguity: a technical failure, an unparseable reviewer verdict, or an extraction that matches the contract ambiguously (e.g. two candidate JSON blocks) all become `FAILED`, never `CHANGES_REQUIRED` or `APPROVED`.
- Keep the change local to `workflow.api`, `workflow.application`, `workflow.domain`, `workflow.infrastructure`, and the shell layer; no changes to `agent-invocation` capability or `PiRunner`/`PiRunResult`.

**Non-Goals:**
- Redesigning `VERIFICATION`/`Verifier` (plan 13's scope). This design does not touch `Verifier`'s signature or the `VERIFICATION` branch of `advance()`, and the `REVIEW`-routing changes here are additive to the existing `switch` structure so plan 13 can modify the `VERIFICATION` arm independently without conflicting with this change's `REVIEW` arm.
- Deciding how the `IMPLEMENTATION` stage is bound to the exact approved change (plan 14's scope). This design only ensures the approved proposal text and user feedback are present in the stage context; it does not add any enforcement that implementation stays within that scope.
- Persistence technology for the new context/feedback fields - `WorkflowRepository` remains an in-memory port exactly as today; the new fields are plain Java fields on `Workflow`, following the existing pattern (`currentStage`, `status`, `outcomes`).
- Designing a retry/resume UI for a `FAILED` workflow caused by a failed extraction (plan 15's scope, per plan 10's design.md Non-Goals, which already deferred this).
- Re-implementing, forking, or providing an alternate path for anything plan 10 or plan 11 already own (terminal-state guards; `PiRunResult`/parser completion semantics). This change calls into those existing contracts only.

## Decisions

**D1: Stage context is a new immutable record built per-invocation by the engine, not a mutable field bag on `Workflow`.**
Add `StageContext` (e.g. `record StageContext(String task, String targetRepo, Optional<String> analysisFindings, Optional<String> proposalOutput, Optional<String> pendingFeedback)`) in `workflow.application` (or `workflow.api`, decided by whether `StageRunner` callers outside the package need it - `AgentStageRunner` is in `workflow.infrastructure` and already depends on `workflow.application`/`workflow.domain`, so `workflow.application` is the natural home, consistent with `StageRunner`/`Verifier` living there). `WorkflowEngineImpl` builds a fresh `StageContext` immediately before each `stageRunner.run(...)` call by reading `workflow.outcomes()` for the latest `PROJECT_ANALYSIS`/`CHANGE_PROPOSAL` outcome and the workflow's own pending-feedback field. `StageRunner.run(WorkflowStage, Workflow, StageContext)` gains the new parameter. Alternative considered: store the assembled context directly on `Workflow` and recompute it on every mutation. Rejected because the context is a derived view (prior outcomes + pending feedback), and deriving it fresh at the one call site that needs it (`advance()`, right before `stageRunner.run`) avoids a second source of truth that could drift from `outcomes()`.

**D2: Pending feedback lives on `Workflow` as a single nullable/`Optional`-backed field, cleared after one consuming stage run, not a queue.**
Add a field such as `private String pendingFeedback` (empty string = none, matching the proposal's "empty string accepted as no feedback") to `Workflow`, with `recordPendingFeedback(String)` and `consumePendingFeedback()` methods; `consumePendingFeedback()` returns the current value and resets it to empty in one call. `WorkflowEngineImpl.requestRevisions(id, feedback)`/`requestFurtherWork(id, feedback)` call `workflow.recordPendingFeedback(feedback)` before `advance(...)`; the `advance()` loop calls `workflow.consumePendingFeedback()` exactly once, when building the `StageContext` for the very next `stageRunner.run(...)` call, so a second, later stage run in the same `advance()` loop (e.g. `CHANGE_PROPOSAL` succeeding and the loop continuing to `VALIDATION_APPROVAL`) does not see stale feedback. Alternative considered: a `List<String>` feedback history attached to the whole workflow. Rejected - the proposal and spec scope this to "next relevant stage only," and a history list raises an unresolved question (how far back do later stages look?) that is out of scope; a single consume-once field directly satisfies the "cleared after use" scenario.

**D3: `ReviewVerdict` and the findings list are top-level additions - `ReviewVerdict` as an enum in `workflow.api`, findings as `List<String>` - both carried as `Optional`-wrapped fields added to `StageOutcome`, not a `REVIEW`-specific subtype of `StageOutcome`.**
`StageOutcome` becomes `record StageOutcome(WorkflowStage stage, boolean success, String output, Optional<ReviewVerdict> verdict, Optional<List<String>> findings)` (existing `success(stage, output)`/`failure(stage, output)` factories keep working by defaulting `verdict` and `findings` to `Optional.empty()`), with a new `StageOutcome.reviewed(WorkflowStage stage, String output, ReviewVerdict verdict, List<String> findings)` factory used only for a technically successful `REVIEW` outcome. Both `verdict` and `findings` are always `Optional.empty()` for every non-`REVIEW` stage and for a technically failed or extraction-failed `REVIEW` outcome. Alternative considered: a sealed interface with `StageOutcome.Review` and `StageOutcome.Standard` variants. Rejected as a larger, cascading change to every existing call site and test that constructs/pattern-matches `StageOutcome` today, for a benefit (type-level enforcement that only `REVIEW` carries a verdict) better captured by D4's extraction/fail-closed logic than by a type hierarchy.

**D4: Verdict/findings extraction happens in `AgentStageRunner`, at the point the `REVIEW` stage's `PiRunResult` is turned into a `StageOutcome`, under the exact contract defined in proposal.md; any failure of that contract is folded into `success = false`.**
Add an extraction step that runs only for `stage == REVIEW` and only when `result.status() == PiRunStatus.SUCCESS` (reusing plan 11's hardened completion contract - a `REVIEW` run that plan 11 would already report as `FAILURE` never reaches extraction at all). The extraction algorithm, applied to `result.finalText()` as a whole:
  1. Scan the text for fenced code blocks introduced by a line matching ```` ```json ```` (case-sensitive, exact tag) and closed by a line that is exactly ```` ``` ````. If more than one such block is found, extraction fails (ambiguous - "multiple ```json blocks").
  2. If exactly one such block is found, its inner content is the candidate document. If no such block is found, the entire trimmed `finalText()` is the candidate document.
  3. Parse the candidate document as JSON. Any parse error fails extraction ("not valid JSON").
  4. The parsed value SHALL be a JSON object. Any other JSON type (array, string, number, boolean, null) fails extraction ("not a JSON object").
  5. The object SHALL contain `verdict` as a string equal to exactly `"APPROVED"` or `"CHANGES_REQUIRED"` (no case normalization, no trimming beyond standard JSON string parsing). Any other value, type, or absence fails extraction ("missing or invalid verdict").
  6. The object SHALL contain `findings` as a JSON array whose every element is a string (the array may be empty). Any other value, type, or absence fails extraction ("missing or invalid findings").
  7. On success, extraction yields exactly the parsed `verdict` (mapped to `ReviewVerdict.APPROVED`/`CHANGES_REQUIRED`) and exactly the parsed `findings` list, with no supplementation from surrounding prose.
If extraction succeeds, return `StageOutcome.reviewed(stage, result.finalText(), verdict, findings)`. If the run was already a `PiRunStatus` failure, or extraction fails for any of the reasons above, return `StageOutcome.failure(stage, <diagnostic naming the specific extraction-failure reason or the original PiRunResult diagnostics>)` with no verdict and no findings - i.e., the fail-closed behavior lives entirely in `AgentStageRunner`, so `WorkflowEngineImpl.advance()`'s `REVIEW` branch can simply check `outcome.success()` first (unchanged technical-failure handling) and then `outcome.verdict()` only when `success()` is `true`. Alternative considered: let `AgentStageRunner` always return `success = true` for a successful process run and have `WorkflowEngineImpl` do the extraction and fail-closed decision. Rejected because `AgentStageRunner` is already the single place mapping agent-specific output shape to `StageOutcome`, and `WorkflowEngineImpl.advance()` should stay agent-output-format-agnostic.

**D5: `advance()`'s `REVIEW` case is split out of the shared `PROJECT_ANALYSIS, CHANGE_PROPOSAL, IMPLEMENTATION, REVIEW` switch arm into its own `case REVIEW`.**
The new case: run `stageRunner.run(REVIEW, workflow, context)`, record the outcome; if `!outcome.success()`, call `workflow.markFailed()` (today a failed `REVIEW` outcome loops to `IMPLEMENTATION`, which the proposal explicitly calls out as a bug this change fixes, since a crash was previously indistinguishable from "changes requested"); if `outcome.success()` and `outcome.verdict()` is empty (should not happen given D4, but defensively checked), call `workflow.markFailed()` with a diagnostic naming the invariant violation; if `outcome.verdict()` is `APPROVED`, `moveTo(ACCEPTANCE)`; if `CHANGES_REQUIRED`, `moveTo(IMPLEMENTATION)`. Alternative considered: keep `REVIEW` in the shared arm and add an `if (stage == REVIEW)` branch inside it. Rejected - the shared arm's `next(stage)` helper assumes a single unconditional success path, and threading verdict-based branching through it is harder to read than a dedicated case; a dedicated case mirrors how `VERIFICATION` already has its own case.

**D6: `WorkflowEngine` port signatures change to `requestRevisions(WorkflowId id, String feedback)` / `requestFurtherWork(WorkflowId id, String feedback)`; no overload is kept.**
This is the proposal's declared **BREAKING** change. `FlowCommands` (Spring Shell) is updated to accept and pass a new feedback argument (empty default when the user supplies none, keeping shell UX backward-compatible even though the Java signature changes). Alternative considered: add an overload (`requestRevisions(WorkflowId)` delegating to `requestRevisions(WorkflowId, "")`) to avoid breaking existing callers. Rejected per the proposal's explicit choice to make this **BREAKING** rather than carry two call paths indefinitely; `FlowCommands` is the only in-repo caller (confirmed by grep), so there is no external consumer to preserve compatibility for before plan 17 adds CLI tests against the shell layer.

## Risks / Trade-offs

- [Risk] Changing `StageOutcome`'s constructor shape (even via a factory) could silently break pattern-matching or positional-record-deconstruction call sites in tests → Mitigation: keep `success(...)`/`failure(...)` factories with their existing two-argument signatures by overloading rather than renaming, and grep all `StageOutcome` constructions/destructurings across `src/test` during implementation (tasks.md task) before relying on the compiler to catch every case, since a record pattern match with a wildcard could silently compile against a changed arity in some match forms.
- [Risk] Folding a technically failed `REVIEW` into `markFailed()` instead of looping to `IMPLEMENTATION` changes existing behavior for any current test that asserts a failed review loops → Mitigation: this is the explicit bug fix called out in the proposal; `WorkflowEngineImplTest`'s existing review-loop tests are read during implementation (tasks.md) to confirm they test `CHANGES_REQUIRED`-shaped (verdict-based) looping, not technical-failure looping, and updated if any test currently asserts the old (now-incorrect) technical-failure-loops behavior.
- [Risk] The exact-JSON extraction contract in `AgentStageRunner` (D4) depends on the reviewer agent's system prompt actually instructing it to emit a single ```` ```json ```` block with exactly `verdict`/`findings` keys - a soft contract with the agent's instructions, not a schema enforced by the agent runtime itself → Mitigation: extraction failure already fails closed per D4/the spec regardless of why the contract was not met (wrong shape, multiple blocks, missing keys, prose-only output); the reviewer agent's prompt is updated in tasks.md to instruct it to emit exactly this shape, and a failure to comply is always a `FAILED` outcome, never a guessed verdict.
- [Risk] Clearing pending feedback after exactly one consuming stage run (D2) could feel surprising if the user expects feedback to persist across multiple correction loops → Mitigation: this matches the proposal's and spec's explicit "consumed once" scenario; if real usage shows feedback needs to persist longer, that is a follow-up change to the `stage-context-propagation` capability, not a reason to delay this one.
