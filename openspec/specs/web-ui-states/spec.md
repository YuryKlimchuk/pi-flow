# web-ui-states Specification

## Purpose
Делает интерфейс пригодным для ручного тестирования: каждое обращение имеет понятное состояние, безопасную ошибку и возможность повторить запрос.

## Requirements

### Requirement: Состояние загрузки
Страница SHALL показывать индикатор загрузки до отображения результата операции GitHub или текущего состояния длительного Workflow.

#### Scenario: Запрос выполняется
- **WHEN** пользователь отправляет запрос списка репозиториев, Issues или состояния workflow
- **THEN** HTML/интерактивный интерфейс показывает состояние loading до результата

### Requirement: Маппинг ошибок
Web SHALL сопоставлять `CONFIGURATION`, `AUTHENTICATION`, `NOT_FOUND`, `RATE_LIMIT`, `NETWORK` и `SERVER` с различимыми сообщениями без технического stack trace.

#### Scenario: Ошибка авторизации
- **WHEN** github возвращает `ErrorType.AUTHENTICATION`
- **THEN** UI сообщает о неверном или недействительном PAT и не предлагает считать ошибку сетевым сбоем

### Requirement: Повтор запроса
При retryable-сбое UI SHALL предоставлять действие, повторяющее исходный запрос с теми же параметрами, включая запрос состояния workflow.

#### Scenario: Сетевой сбой
- **WHEN** операция завершается `NETWORK` с `retryable=true`
- **THEN** пользователь видит кнопку/ссылку retry, сохраняющую исходные параметры запроса

### Requirement: Контекст репозитория
Переходы между страницами Issues SHALL сохранять owner и repository в адресе запроса.

#### Scenario: Переход по странице
- **WHEN** пользователь переходит на следующую страницу Issues
- **THEN** выбранный репозиторий остаётся тем же и передаётся в `IssueOperations`

### Requirement: Адаптивное представление
Основные элементы страниц SHALL оставаться доступными при ширине viewport от 320 CSS px.

#### Scenario: Узкий экран
- **WHEN** страница открыта с viewport 320 px
- **THEN** контент не требует горизонтальной прокрутки для чтения списка и основных действий

### Requirement: Состояние долгого workflow
Web SHALL различать состояния выполнения Analyst, успешного результата и ошибки workflow.

#### Scenario: Выполнение Analyst
- **WHEN** polling получает состояние `RUNNING` на этапе `ANALYZING_REQUIREMENTS`
- **THEN** UI отображает индикатор работы Analyst, а не финальный результат

#### Scenario: Успешный результат
- **WHEN** polling получает валидный результат анализа
- **THEN** UI прекращает polling, показывает текст результата и действие продолжения

#### Scenario: Ошибка
- **WHEN** polling получает статус `FAILED`
- **THEN** UI прекращает polling и показывает сообщение об ошибке без stack trace
