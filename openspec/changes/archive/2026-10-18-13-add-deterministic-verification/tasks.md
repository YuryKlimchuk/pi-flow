## 3. Command-running verifier implementation

- [x] 3.1 Implement the new `Verifier` implementation (e.g. `CommandVerifier`) in `workflow.infrastructure` as the `@Component` replacing `AlwaysPassVerifier`: on every `verify(Workflow)` call, read the target repository's configuration file fresh (task 2.2); if absent, return `VerificationResult.notConfigured("No verification configuration file found at <resolved path>")`; if invalid, return `VerificationResult.infrastructureError(<reason naming the specific schema/read problem>)` - in neither case starting a process; verify with a `CommandVerifierTest` case for each, asserting the call completes without any process being started (confirmed by code reading: both branches return before any `ProcessBuilder` use).
- [x] 3.2 Implement the process-running path: build a `ProcessBuilder` from the configured argument vector, set its working directory to the configured override or the workflow's target repository, merge stdout+stderr (`redirectErrorStream(true)`), attempt to start the process, and if starting the process itself fails (executable not found, permission denied, configured working directory does not exist), return `VerificationResult.infrastructureError(<reason naming the start failure>)` without reporting `FAILED`; verify with `CommandVerifierTest` cases: a configuration naming a nonexistent executable, and a configuration naming a nonexistent working directory, each asserting `INFRASTRUCTURE_ERROR` and a reason distinguishable from a command-ran-and-failed reason.
- [x] 3.3 Continue the process-running path for a successfully started process that completes within the configured timeout: map exit code 0 to `VerificationResult.passed(...)`, nonzero exit code to `VerificationResult.failed(...)`; verify with `CommandVerifierTest` cases using real short-lived test scripts/executables (e.g. `sh -c "exit 0"` and `sh -c "exit 1"`) asserting `PASSED` and `FAILED` respectively, each distinguishable in the test from the `INFRASTRUCTURE_ERROR` cases in task 3.2 and task 3.4.
- [x] 3.4 Implement timeout handling: if a successfully started process does not exit within the configured timeout, destroy it (reusing the destroy-tree pattern read from `JsonModePiRunner.destroyTree`) and return `VerificationResult.infrastructureError(...)` with a report noting the timeout (not `FAILED` - the command's own exit code was never observed, so this is a technical/infrastructure problem with the verification mechanism itself, not a reported content issue, per design.md's distinguishing rule); verify with a `CommandVerifierTest` case using a deliberately hanging test command (e.g. `sh -c "sleep 30"`) with a short configured timeout, asserting `INFRASTRUCTURE_ERROR` (not `FAILED`) and a report mentioning the timeout, and that the test itself completes quickly.
- [x] 3.5 Implement bounded output capture per design.md D3: read process output into a capped buffer (fixed constant, e.g. 20000 characters), discarding further bytes once the cap is reached, and setting `truncated = true` when the cap was hit; verify with a `CommandVerifierTest` case using a test command that prints more than the bound, asserting the result's `report()` length is at most the bound and `truncated() == true`, and a separate case asserting a report within the bound is not flagged as truncated.
- [x] 3.6 Add a `CommandVerifierTest` case asserting the configured working-directory override is honored (e.g. a test command that prints its working directory) and a separate case asserting the target repository path is used when no override is configured.
- [x] 3.7 Add a `CommandVerifierTest` case demonstrating live reconfiguration within one running test (no application restart involved, consistent with task 2.3's reader-level test but exercised through the full `Verifier`): call `verify(workflow)` with no configuration file present (expect `NOT_CONFIGURED`), write a valid configuration file, call `verify(workflow)` again on the same `Verifier` instance (expect `PASSED` or `FAILED` depending on the configured command), asserting no restart or new `Verifier` instance was needed.
