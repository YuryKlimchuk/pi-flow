# workflow-lifecycle Specification

## Purpose
Определяет наблюдаемое поведение и публичный жизненный цикл Workflow как владельца состояния бизнес-процесса разработки.

## Requirements

### Requirement: Создание Workflow
Публичный контракт `workflow` SHALL создавать Workflow с уникальным идентификатором, контекстом выбранного репозитория и Issue, статусом `CREATED` и этапом `ANALYZING_REQUIREMENTS`.

#### Scenario: Валидная команда запуска
- **WHEN** команда содержит идентификатор репозитория, номер задачи и непустой идентификатор workflow
- **THEN** результат содержит тот же идентификатор и состояние `CREATED` на этапе `ANALYZING_REQUIREMENTS`

#### Scenario: Валидная команда запуска по Issue
- **WHEN** команда содержит owner, repository, положительный issue number и непустой идентификатор workflow
- **THEN** результат содержит контекст репозитория, номер Issue, тот же идентификатор и состояние `CREATED` на этапе `ANALYZING_REQUIREMENTS`

#### Scenario: Невалидная команда
- **WHEN** отсутствует owner или repository либо номер задачи не положителен
- **THEN** команда отклоняется типизированной ошибкой валидации и Workflow не создаётся

### Requirement: Модель состояния Workflow
Workflow SHALL предоставлять текущий этап, актуальный результат ручного gate и неизменяемую историю всех завершённых шагов с их результатами; после Continue старый результат SHALL оставаться доступным только через историю.

#### Scenario: Чтение состояния
- **WHEN** вызывающая сторона запрашивает состояние созданного Workflow
- **THEN** получает идентификатор, статус, текущий этап, пустую историю шагов и контрольные точки через публичный контракт

#### Scenario: Чтение результата
- **WHEN** вызывающая сторона запрашивает состояние workflow после успешного анализа
- **THEN** получает текущий результат анализа и отдельную запись анализа в истории шагов

#### Scenario: Состояние следующего этапа
- **WHEN** Workflow успешно продолжен после анализа
- **THEN** состояние содержит `currentStage=DESIGNING_SOLUTION`, а результат анализа остаётся доступным в истории

#### Scenario: Состояние rework
- **WHEN** rework принят до завершения нового анализа
- **THEN** состояние содержит текущий этап анализа, не публикует старый результат как актуальный и сохраняет старый результат в истории

### Requirement: Допустимые переходы
Домен Workflow SHALL разрешать переход с ручного gate на следующий этап ровно один раз и SHALL сохранять результат каждой завершённой итерации этапа перед переходом или rework. После успешного Architect gate Workflow SHALL разрешать создание итоговой ветки, а после успешной публикации SHALL переходить в `COMPLETED`.

#### Scenario: Переход после Analyst
- **WHEN** Workflow в `WAITING_FOR_USER` после успешного анализа и пользователь принимает «Продолжить»
- **THEN** статус становится `RUNNING`, текущим этапом становится `DESIGNING_SOLUTION`, а результат анализа добавляется в историю

#### Scenario: Переход после Architect
- **WHEN** Workflow в `WAITING_FOR_USER` после успешного Architect proposal и пользователь принимает «Продолжить»
- **THEN** статус становится `RUNNING`, текущим этапом становится `IMPLEMENTING`, а proposal остаётся в истории

#### Scenario: Создание итоговой ветки
- **WHEN** Workflow имеет утверждённые анализ и proposal Architect
- **THEN** команда создания ветки принимается, создаёт итоговую ветку с предложенным Analyst именем и переводит workflow в состояние, в котором доступен push

#### Scenario: Завершение после push
- **WHEN** локальный коммит и публикация ветки завершены успешно
- **THEN** статус Workflow становится `COMPLETED`, а результат публикации сохраняется в истории

#### Scenario: Запрещённый переход
- **WHEN** вызывающая сторона запрашивает переход, не разрешённый из текущего состояния
- **THEN** состояние Workflow не изменяется и возвращается ошибка недопустимого перехода

#### Scenario: Повторное продолжение
- **WHEN** пользователь повторно отправляет команду продолжения вне ручного gate
- **THEN** домен отклоняет команду и не добавляет новый этап в историю

#### Scenario: Rework текущего этапа
- **WHEN** Workflow имеет результат текущего этапа и получает непустой feedback
- **THEN** текущий результат сохраняется в истории, публикуемый результат очищается, а статус становится `RUNNING`

### Requirement: Публичный запуск Workflow
Публичный API `workflow` SHALL предоставлять команды запуска, запроса состояния, продолжения после анализа и повторного анализа с feedback.

#### Scenario: Вызов из web
- **WHEN** web передаёт команду запуска через `workflow.api`
- **THEN** workflow возвращает публичный идентификатор и состояние запуска без доступа web к внутренним пакетам

#### Scenario: Вызов продолжения из web
- **WHEN** web передаёт публичную команду продолжения для workflow с валидным результатом анализа
- **THEN** workflow принимает команду без доступа web к внутренним пакетам

#### Scenario: Продолжение до результата анализа
- **WHEN** команда продолжения относится к workflow без завершённого анализа
- **THEN** команда отклоняется типизированной ошибкой и состояние workflow не изменяется

#### Scenario: Вызов rework из web
- **WHEN** web передаёт публичную команду rework с workflow id и feedback
- **THEN** workflow принимает команду без доступа web к domain, application или infrastructure типам

#### Scenario: Rework без feedback
- **WHEN** команда rework содержит пустой или состоящий только из пробелов feedback
- **THEN** команда отклоняется типизированной ошибкой валидации и состояние не изменяется

### Requirement: Границы ответственности Workflow
Workflow SHALL координировать создание состояния и запуск длительного исполнения через публичные контракты, SHALL NOT выполнять локальные Git-операции самостоятельно и SHALL NOT вызывать `agent.run` в минимальном сценарии до клонирования репозитория.

#### Scenario: Координация зависимостей
- **WHEN** минимальный запуск требует подготовки workspace и технического запуска агента
- **THEN** workflow вызывает `workspace.api` и `agent.api`, а не JGit, `Process`, GitHub HTTP-клиент или Pi напрямую

#### Scenario: Минимальная координация
- **WHEN** валидная команда запуска передана
- **THEN** workflow создаёт состояние и инициирует execution, не вызывая агент и не импортируя Git/JGit реализацию
