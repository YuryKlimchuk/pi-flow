# Design

## Context

See proposal.md - Why for the optimistic-success gap. Current state, read from `PiJsonlParser` and `JsonModePiRunner`:

- `PiJsonlParser` tracks `streamedText`, `authoritativeText`, `settled`, `failed`, `failureReason`. It recognizes three event types (`message_update`/`text_delta`, `message_end`, `agent_settled`); anything else, including every malformed line, is silently ignored by `accept()` (`catch (JacksonException e) { ... return; }` with only a debug log).
- `JsonModePiRunner.toResult()` computes `status = (exitCode != 0 || parser.failed()) ? FAILURE : SUCCESS` - it never checks `parser.settled()` or whether `finalText()` is non-blank, so exit 0 plus a silently-dropped malformed stream, or exit 0 with zero stdout lines, currently yields SUCCESS with empty `finalText()`.
- `diagnostics` in `toResult()` is `stderr` text, falling back to `parser.failureReason()` only if `stderr` is empty - so a present-but-generic stderr line can hide a specific `failureReason` today; this change does not need to fix that specific precedence bug beyond ensuring the final, specific reason is available and preferred when stderr is empty, which is already the existing precedence - the real preservation gap is that `failureReason` can be overwritten by a later generic signal and that intermediate vs. terminal is not tracked at all.
- Reader threads (`startStdoutReader`, `startStderrReader`) are daemon threads joined via `joinQuietly` with a fixed 5s timeout on every path (success, timeout, interrupted); this part already runs on every exit path per `runCommand()`'s structure - the gap is not join-on-every-path (already true) but ensuring a reader thread's late-accumulated text cannot retroactively justify SUCCESS once the parser/exit-code-derived verdict is FAILURE.
- No existing code inspects or records a Pi protocol/version marker; `agent_settled`/`message_end`/`message_update` are assumed to always be the current shape.
- No existing distinction between intermediate and terminal errors: `failed`/`failureReason` are set once and never reconsidered if a later event arrives.

## Goals / Non-Goals

**Goals:**
- Make `PiJsonlParser`/`toResult()` require a recognized completion signal and non-blank text (or an explicit non-error terminal signal) before reporting SUCCESS, closing the "exit 0 + empty/garbled stream = SUCCESS" gap.
- Track whether any recognized event type was seen at all, to distinguish "no supported protocol detected" from "recognized protocol, but run failed."
- Preserve the specific `failureReason` end-to-end into `diagnostics()` without being silently replaced by a less specific message.
- Add a narrow, protocol-demonstrated intermediate-vs-terminal error distinction: only recognized when a later successful event in the same run follows an earlier error event.
- Keep `TIMEOUT` vs `FAILURE` vs process-start failure distinguishable, and make the FAILURE diagnostics text identify which category (empty/malformed/missing-completion/unsupported-protocol/terminal-error) applies.
- Prevent late/async reader-thread text from upgrading an otherwise-failed run to SUCCESS.

**Non-Goals:**
- Negotiating or requesting a specific Pi CLI version at process-start time (e.g. invoking `pi --version` as a pre-flight check). This change only validates the shape of the JSONL stream actually received, not the CLI binary's version string.
- Introducing a new `PiRunStatus` enum value for "recovered intermediate error." The intermediate-vs-terminal distinction affects only whether the run is ultimately reported SUCCESS or FAILURE; it does not need a third status value for this change.
- Changing the `PiRunner` port interface (`run(String)`, `run(String, String, String)`) or `PiRunResult`'s field set (`status`, `finalText`, `diagnostics`). If investigation during implementation shows a field is genuinely needed, that is an open question below, not a decision made here.
- Redesigning retry/backoff behavior for failed runs (covered by plan 15, per task scope boundaries).
- Adding metrics/structured diagnostics logging beyond existing SLF4J usage (covered by plan 16).

## Decisions

**D1: Completion/success gate lives in `PiJsonlParser`, exposed as a new query method, not computed solely in `JsonModePiRunner.toResult()`.**
Add a method such as `PiJsonlParser.hasRecognizedCompletion()` (true once a `message_end` with non-error stop reason is followed by, or coincides with, a non-aborted `agent_settled`, or - for the narrow recovery case - once any terminal non-error settlement is reached regardless of earlier errors) alongside the existing `settled()`/`failed()`/`finalText()`. `toResult()` combines `exitCode == 0 && parser.hasRecognizedCompletion() && !parser.finalText().isBlank() && !parser.failed()` to decide SUCCESS. Alternative considered: compute everything inline in `toResult()` by calling `settled()`/`failed()`/`finalText()` and adding ad hoc blank/length checks there. Rejected because the recovery logic (replaying whether a later success follows an earlier error) needs access to the event sequence, which only the parser has; keeping that logic in `PiJsonlParser` keeps `JsonModePiRunner` a thin process/thread wrapper, matching the project's existing split (parser is pure/unit-testable, runner is the only class touching `Process`).

**D2: Protocol-recognition tracking is a boolean flag (`sawRecognizedEvent`) set in `accept()`, not a version string comparison.**
`PiJsonlParser.accept()` already switches on `node.path("type").asText()`; add a flag set to `true` whenever that switch matches one of the three known cases (not the `default` branch), and expose it as `supportedProtocolObserved()` (or similar). A stream where every line is either unparseable JSON or parses but hits the `default` case leaves this flag `false`, and `toResult()` treats that as FAILURE with a diagnostic naming the missing protocol signal. Alternative considered: have `JsonModePiRunner` call `pi --version` before the real run and gate on a known-good version string. Rejected per the Non-Goals above - it adds a second process invocation per run, couples this change to a specific CLI versioning scheme that does not exist yet in the codebase (confirmed by grep: no version-string handling anywhere), and does not address the actual observed gap, which is about the shape of the JSONL stream received, not the CLI's self-reported version.

**D3: `failureReason` becomes multi-valued internally (list or last-wins-but-tracked) only insofar as needed to support the intermediate/terminal distinction; the public `diagnostics()` string stays a single string.**
`PiJsonlParser` keeps `failed`/`failureReason` as today but re-evaluates them on each `handleMessageEnd`/`handleSettled` call: an error-bearing `message_end` sets `failed = true` and records the reason as today; if a *later* `message_end` reports a non-error stop reason and the stream subsequently settles with `aborted: false`, the parser clears `failed` back to `false` (the "recovery" case) while retaining the last reason seen for diagnostics purposes only if the run ultimately still fails for another reason. `JsonModePiRunner.toResult()`'s existing precedence (`stderr` first, then `parser.failureReason()`) is unchanged; this decision only changes what `parser.failed()`/`parser.failureReason()` report at the point `toResult()` reads them. Alternative considered: keep `failed` as a one-way latch (today's behavior) and instead have `JsonModePiRunner` separately decide to override it. Rejected because the parser is the only component that sees the full ordered event sequence; `JsonModePiRunner` sees only the parser's final snapshot after the stream ends, so it cannot itself tell "recovered" from "never failed."

**D4: Reader-thread "late text" safeguard is a consequence of D1, not a separate synchronization mechanism.**
Because `joinQuietly(stdoutThread, stderrThread)` already runs before `toResult()` is called on every exit path (confirmed by reading `runCommand()`), by the time `toResult()` evaluates `parser.hasRecognizedCompletion()`/`finalText()`, the reader thread has either finished normally or been joined with a bounded wait after `destroyTree()`. No new thread-safety mechanism is introduced; the fix is purely that `toResult()` now requires `hasRecognizedCompletion()` (D1) in addition to non-blank text, so a reader thread that only ever accumulated stray `text_delta` fragments without a completion event cannot produce SUCCESS merely because `finalText()` is non-empty. Alternative considered: add explicit locking/visibility annotations around `PiJsonlParser`'s fields. Rejected - `PiJsonlParser` is only ever written to by the single stdout-reader thread and only ever read by the runner thread after that reader thread has been joined, so no concurrent access exists to guard against; the existing design is already safe for this access pattern.

**D5: Diagnostic text identifies the failure category via distinct, literal substrings, not a new structured field.**
Each new failure path (empty stream, malformed-only stream, missing completion, unsupported protocol, terminal error, process-start failure) produces `diagnostics()` text containing a distinct identifying phrase (exact wording decided in tasks.md/implementation, not fixed here) so tests and operators can `contains(...)`-match the category without parsing a structured error code. Alternative considered: add a `FailureCategory` enum field to `PiRunResult`. Rejected per Non-Goals - it changes the `PiRunResult` record shape, which this change intentionally avoids; a future diagnostics-focused change (plan 16) is the better place to decide if structured categories are worth the API change.

## Risks / Trade-offs

- [Risk] Requiring non-blank `finalText()` for SUCCESS could reject a legitimate run that completes with genuinely empty assistant output (e.g. a tool-only response with no final text) → Mitigation: scope this change's "must have non-blank text" rule to the exit-0-with-empty/malformed-stream case described in the proposal; if a tool-only completion is a real scenario Pi can produce, the recognized-completion check (`hasRecognizedCompletion()`) plus `agent_settled` with `aborted: false` is the primary success signal, and the design leaves room in D1 to treat a settled, non-aborted run as success even with blank text if investigation during implementation shows real Pi output can be legitimately empty - flagged as an open question below.
- [Risk] The intermediate-vs-terminal recovery logic (D3) could mask a real failure if a flaky later `message_end` happens to report a non-error stop reason without the agent actually having recovered → Mitigation: the recovery condition is narrow and requires the *final* settlement (`agent_settled` with `aborted: false`) in addition to a later non-error `message_end`, matching the proposal's requirement to only apply this "where the protocol actually demonstrates the recovery”; negative tests cover the terminal-error case explicitly.
- [Risk] Changing `toResult()`'s SUCCESS condition is **BREAKING** for any caller or test currently relying on exit-0-implies-SUCCESS → Mitigation: this is called out as BREAKING in the proposal; `JsonModePiRunnerTest`/`PiJsonlParserTest` are updated in tasks.md to cover both the old passing cases (still SUCCESS, since they all do produce `agent_settled` + non-blank text, confirmed by reading the existing fixture-based tests) and the new failing cases, so no currently-passing test asserts behavior this change removes.

## Open Questions

- Whether a settled (`agent_settled`, `aborted: false`), non-error run with genuinely blank `finalText()` (e.g. a pure tool-call-only turn) should be SUCCESS or FAILURE under this change's stricter rule. Deferred: resolve during implementation by checking whether the `fake-pi` fixtures or real Pi JSON-mode output ever produce that shape; if they do, relax D1's blank-text check for the settled-and-not-aborted case specifically. This does not change the specs or task breakdown's overall shape - only whether one edge-case test asserts SUCCESS or FAILURE.
