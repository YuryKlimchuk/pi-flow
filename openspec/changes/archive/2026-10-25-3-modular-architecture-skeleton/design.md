# Design

## Context

См. `proposal.md` — Why. Состав модулей и направления зависимостей зафиксированы в capability `modular-architecture`. Базовый пакет приложения — `com.hydroyura.agents.piflow`. Spring Modulith уже подключён в `pom.xml`.

## Goals / Non-Goals

**Goals:**
- Создать минимальный каркас шести модулей, видимых Spring Modulith.
- Добавить архитектурный тест проверки границ.

**Non-Goals:**
- Не добавляется бизнес-логика, порты/адаптеры, контроллеры, репозитории, сущности.
- Не настраивается Temporal, Pi, Git, GitHub интеграция.

## Decisions

### D1: Модули размещаются под базовым пакетом

Каждый модуль — пакет `com.hydroyura.agents.piflow.<module>` с `package-info.java`, помеченным `@org.springframework.modulith.ApplicationModule`.

- **Почему**: соответствует базовому пакету приложения и стандартной структуре Spring Modulith.
- **Альтернатива**: корневой пакет без подпакетов — отклонено.

### D2: Только пустые DDD-слои

Создаются пустые подпакеты `api`, `domain`, `application`, `infrastructure` в модулях бизнес-логики (`workflow`, `workspace`, `agent`, `interaction`, `github`); `web` — как адаптер без этих слоёв.

- **Почему**: фиксирует границы без преждевременной реализации.
- **Альтернатива**: полная реализация слоёв — отклонено (это следующий шаг).

### D3: Один архитектурный тест на границы

Тест использует `ApplicationModules.of(PiFlowApplication.class)` и вызывает `verify()` для проверки отсутствия циклов.

- **Почему**: минимальная проверка, достаточная для каркаса.
- **Альтернатива**: детальные ArchUnit-правила — отложено до появления реальных зависимостей.

## Risks / Trade-offs

### R1: Пустой каркас ничего не проверяет по направлениям зависимостей

[Risk] Без реального кода между модулями тест проверяет только отсутствие циклов, но не направления. → Mitigation: направления зависимостей зафиксированы в `modular-architecture` и будут проверяться при появлении кода.
