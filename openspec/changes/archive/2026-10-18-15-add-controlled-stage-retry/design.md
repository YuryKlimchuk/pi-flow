# Design

## Context

See proposal.md - Why for the no-general-retry, unconfigurable-loop-guard, and FAILED-with-no-recovery gaps.

Current state, read directly from `src/main/java/.../workflow/api/WorkflowStatus.java`, `WorkflowStage.java`, `StageOutcome.java`, `workflow/domain/Workflow.java`, and `workflow/application/WorkflowEngineImpl.java` as of this writing:

- `WorkflowStatus` has exactly five values: `IN_PROGRESS`, `AWAITING_USER`, `COMPLETED`, `CANCELLED`, `FAILED`. There is no paused-but-retryable status today.
- `WorkflowEngineImpl.advance()` loops `while (status == IN_PROGRESS)`, incrementing a local `steps` counter capped at `MAX_ADVANCE_STEPS = 50`; exceeding it calls `workflow.markFailed()` directly, with no recovery path. `REVIEW` returning `outcome.success() == false` and `VERIFICATION` returning a boolean `false` both loop to `IMPLEMENTATION` identically today - neither distinguishes "the stage crashed/timed out" from "the stage ran fine and reported a content problem."
- `StageOutcome` is a 3-field record (`stage`, `success`, `output`) with no attempt-kind classification.
- `Workflow.isTerminal()` treats `COMPLETED`, `CANCELLED`, `FAILED` as the only terminal statuses; this is correct and this change does not alter it.
- `WorkflowEngine` has exactly six methods today: `start`, `status`, `approve`, `reject`, `requestRevisions`, `requestFurtherWork`. There is no `retryStage`/`retryVerification`/`retry*` method of any kind.
- Plans 10 (transition guards), 12 (`ReviewVerdict`/`StageOutcome` shape), 13 (`VerificationResult`/`NOT_CONFIGURED`/deterministic verification), and 14 (change-binding) are **planned but not implemented** in `src/main/java` as of this writing (confirmed: no `RetryProperties`, `VerificationResult`, `ReviewVerdict`, or status beyond the five listed above exist in the compiled source tree). This change's tasks.md therefore specifies a strict implementation order rather than a dual "if X is implemented first / otherwise" fallback: **this change (15) is implemented after 10, 12, 13, and 14 are implemented**, consuming their landed shapes as fixed inputs. No task in this change hedges against an alternate ordering; if a dependency is not yet landed when work on this change begins, the correct action is to implement that dependency first, not to improvise its shape here.
- `AgentProperties`/`PiProperties` are the established `@ConfigurationProperties` pattern (`pi-flow.*` prefixes) this change follows for its own budget configuration.

## Goals / Non-Goals

**Goals:**
- Introduce an explicit `PAUSED` workflow status, distinct from `AWAITING_USER`, that represents a workflow stopped by a *retryable technical failure* with retry budget remaining. `AWAITING_USER` continues to mean exactly what it means today: an ordinary gate waiting on a human decision (`VALIDATION_APPROVAL`, `ACCEPTANCE`, and plan 13's `NOT_CONFIGURED` verification pause). The two are never conflated: a gate never reports `PAUSED`, and a technical-failure pause never reports `AWAITING_USER`.
- Change the routing at the budget boundary introduced by this change: where the pre-15 behavior (and plan-10's immediate `markFailed()` on `MAX_ADVANCE_STEPS` overflow) sent an unrecoverable technical failure straight to `FAILED`, this change routes it to `PAUSED` instead, as long as the technical-retry budget for that stage-attempt-sequence is not yet exhausted. Only *exhausting* the budget (the attempt that consumes the last remaining retry and still fails, or a retry request made with zero budget left) results in `FAILED`. `COMPLETED`, `CANCELLED`, and `FAILED` remain terminal and immutable exactly as plan 10 defines; this change adds no exit from any of them.
- Add exactly one general, manually-invoked retry action (`retryStage`), usable at `PAUSED` and (per plan 13's `NOT_CONFIGURED`) at the specific `AWAITING_USER` verification-pause, with no duplicate or parallel retry API.
- Classify every retry attempt as a technical failure or a content correction, and preserve that classification in the recorded, append-only history.
- Replace `MAX_ADVANCE_STEPS` with two independently configurable, explicitly defaulted budgets.
- Require explicit operator acknowledgement (`--acknowledge-partial-changes`) before a manual retry of a write stage (`CHANGE_PROPOSAL`, which writes OpenSpec change artifacts, and `IMPLEMENTATION`, which writes target-repository source files), and never auto-retry a write stage as a technical-failure retry - while keeping the existing content-correction loop (which also re-runs `IMPLEMENTATION`/`CHANGE_PROPOSAL` as normal control flow for a validly-executed stage) unaffected by that prohibition.

**Non-Goals:**
- Automatic (unattended) retry of any kind, for any stage. Auto-retry is disabled by default and this change does not add a configuration path to enable it; every retry is a discrete, explicit, user-initiated command. (The pre-existing content-correction loop - `REVIEW`/`VERIFICATION` routing back to `IMPLEMENTATION` inside `advance()` - is not "auto-retry" in this sense: it is the orchestrator's own normal control flow for a validly-executed stage reporting a content problem, bounded by the content-correction budget, and is unchanged in kind by this proposal, only bounded more explicitly.)
- Making `CHANGE_PROPOSAL`, `IMPLEMENTATION`, or any other write stage retryable, as a technical-failure retry, without an explicit, informed operator decision. A write stage is never re-run by the orchestrator on its own as a technical-failure retry; a human must pass `--acknowledge-partial-changes` to retry one manually. (This Non-Goal is scoped to the technical-failure retry mechanism specifically; it does not extend to, and does not disable, the orchestrator's pre-existing content-correction loop, which is unchanged in kind by this proposal.)
- Changing plan 10's terminal-state immutability guarantee. `COMPLETED`, `CANCELLED`, `FAILED` remain the only terminal statuses, with no new transition out of any of them. `PAUSED` is explicitly non-terminal.
- Redesigning plan 12's `ReviewVerdict`/`StageOutcome` shape or plan 13's `VerificationResult`/`NOT_CONFIGURED`/configuration-reload mechanism. This change consumes those shapes as implemented, generalizing plan 13's narrow verification-retry entry point into the one general retry command rather than replacing plan 13's underlying config-reload behavior.
- A second, parallel retry command. Plan 13's verification-retry capability is generalized into `retryStage`/`flow-retry`; no `retryVerification`/`flow-retry-verification` command coexists with it once this change lands.

## Decisions

**D1: Add `PAUSED` as a sixth, explicitly non-terminal `WorkflowStatus`.**
`WorkflowStatus` gains `PAUSED` alongside the existing five values. `Workflow.isTerminal()` is unchanged in logic (`COMPLETED`, `CANCELLED`, `FAILED` only) and therefore already correctly reports `PAUSED` as non-terminal with no edit needed beyond adding the enum constant and a `markPaused()` mutator on `Workflow`. `PAUSED` is entered only by `WorkflowEngineImpl` when a stage's execution fails technically (process crash, timeout, malformed/unparseable output) for an eligible, non-write stage and the technical-retry budget for that stage-attempt-sequence has at least one attempt remaining. `AWAITING_USER` is never used for this purpose and keeps its current, sole meaning: an ordinary human decision gate.
Alternative considered: reuse `AWAITING_USER` for technical-failure pauses too, distinguishing them only via the latest `StageOutcome`'s new `attemptKind`/success fields. Rejected - the proposal requires an explicit, distinguishable status so that status alone (without inspecting outcome history) tells an operator or a monitoring query whether a workflow is blocked on a *human decision* (`AWAITING_USER`) or on a *retryable technical problem* (`PAUSED`); overloading one status for both would force every caller to also inspect the outcome history just to know which kind of unblocking action applies.

**D2: The budget boundary changes routing from `FAILED` to `PAUSED`; only budget exhaustion still produces `FAILED`.**
Before this change, any technical failure of a stage inside `advance()`'s dispatch (an uncaught exception from `StageRunner`/`Verifier`, once plan 10 catches and records it as a failed outcome, or `MAX_ADVANCE_STEPS` overflow) results immediately in `workflow.markFailed()`. This change replaces that immediate-failure routing for *eligible, non-write* stages: on a technical failure, `WorkflowEngineImpl` checks the stage's technical-retry counter against `RetryProperties.maxTechnicalRetries`. If the counter has not yet reached the budget, the workflow transitions to `PAUSED` (not `FAILED`), the counter is incremented, and the failed attempt is recorded with `AttemptKind.TECHNICAL_RETRY` (or `AttemptKind.INITIAL` if this is the stage's first-ever attempt - see D3). If the counter has already reached the budget - i.e. this failing attempt is the one that exhausts it, or a `retryStage` call is made when the counter already equals the budget - the workflow transitions to `FAILED` instead, exactly as before. `CHANGE_PROPOSAL`, `IMPLEMENTATION`, and any other write stage are explicitly excluded from automatic `PAUSED` routing on their own (D5): a technical failure of a write stage still requires the operator's explicit, informed `--acknowledge-partial-changes` decision at the moment of retry (not at the moment of failure) before the orchestrator will re-run it, because the orchestrator cannot safely leave a partially-written artifact set (OpenSpec change files for `CHANGE_PROPOSAL`, target-repository source for `IMPLEMENTATION`) in a stopped-but-presumed-retryable state without that decision.
Alternative considered: route every technical failure to `PAUSED` regardless of remaining budget, and only transition to `FAILED` on a subsequent *rejected* `retryStage` call. Rejected - this would leave a workflow sitting in `PAUSED` with zero actionable budget, misrepresenting it as "retryable" when it is not; the proposal requires that exhaustion itself (the failing attempt that uses the last budget) is what produces `FAILED`, not a later no-op rejection.

**D3: `AttemptKind` (`INITIAL`, `TECHNICAL_RETRY`, `CONTENT_CORRECTION`) is an explicit field on `StageOutcome`, set at the point the outcome is created.**
Extend `StageOutcome` (consuming plan 12/13's already-landed fields, since this change is implemented after them per the Context's strict-ordering note) with `AttemptKind attemptKind`, defaulted to `INITIAL` by the existing `success(...)`/`failure(...)` factories so no pre-existing call site breaks. `WorkflowEngineImpl` sets `TECHNICAL_RETRY` explicitly when recording the outcome of a `retryStage`-triggered re-run of a technically-failed stage (and, per D6, the first-failure attempt that transitions to `PAUSED` is itself recorded as `TECHNICAL_RETRY` from the second attempt onward - the very first attempt at a stage is always `INITIAL` regardless of outcome). It sets `CONTENT_CORRECTION` explicitly when the `advance()` loop's own routing sends `REVIEW`'s `CHANGES_REQUIRED` verdict or `VERIFICATION`'s `FAILED` result back to `IMPLEMENTATION`. `Workflow.outcomes()` remains the single, append-only, ordered history; no second list is introduced, and no prior entry is ever overwritten or removed.
Alternative considered: infer the kind after the fact by diffing consecutive outcomes for the same stage. Rejected - the spec requires "each recorded attempt... identifies which kind it was," which an explicit field satisfies directly and unambiguously; inference is fragile and reconstructs intent from a sequence of flags.

**D4: Verifier failures are split by cause: a nonzero/failing exit code is a content correction; a process-start or execution timeout is a technical pause.**
Plan 13's `VerificationResult` carries a `VerificationStatus` (`PASSED`/`FAILED`/`NOT_CONFIGURED`) plus a bounded report. This change requires `WorkflowEngineImpl`'s `VERIFICATION` routing to distinguish, within what plan 13 reports as `FAILED`, two causes that `VerificationResult`'s report already captures (per plan 13's design: exit code, and whether the command completed within its timeout):
- A **nonzero exit code from a command that started and completed within its timeout** indicates the configured check ran validly and found a content problem (e.g. a failing test suite, a lint violation). This SHALL be classified as a **content correction**: `advance()` loops back to `IMPLEMENTATION`, the content-correction counter increments, and the outcome is recorded with `AttemptKind.CONTENT_CORRECTION` - unchanged in kind from today's behavior, now explicitly classified and budgeted.
- A **failure to start the configured command's process at all, or a timeout before the command completed**, indicates the verification mechanism itself did not execute validly - this is an infrastructure/execution problem, not a finding about the target repository's content. This SHALL be classified as a **technical failure**: the workflow transitions to `PAUSED` (per D2, since `VERIFICATION` is a non-write, retry-eligible stage) if technical-retry budget remains, the technical-retry counter increments, and the outcome is recorded with `AttemptKind.TECHNICAL_RETRY`.
`NOT_CONFIGURED` is unchanged from plan 13's own design: it is neither a content correction nor a technical failure in this sense; it pauses at `AWAITING_USER` (D7), not `PAUSED`, because the cause is a human-fixable configuration gap, not a transient technical glitch worth a bounded auto-countable retry budget.
Alternative considered: classify every non-`PASSED` verification result identically (as today's single boolean does). Rejected - the proposal explicitly requires distinguishing "the check ran and found a problem" from "the check didn't run," since conflating them would let a flaky process-timeout exhaust the same budget as (or be reported identically to) genuine content issues, and vice versa misclassify infra flakiness as a content problem needing a code fix.

**D5: Eligibility for manual retry: non-write stages may be retried per D2's budget check alone; write stages require an explicit `--acknowledge-partial-changes` flag and are never auto-retried as a technical-failure retry.**
`PROJECT_ANALYSIS`, `REVIEW`, and `VERIFICATION` are retry-eligible on a technical failure with budget remaining, and `retryStage` for these requires no special flag beyond identifying the workflow. `CHANGE_PROPOSAL` and `IMPLEMENTATION` are both write stages - `CHANGE_PROPOSAL` because its agent invocation creates or revises OpenSpec change artifact files on disk (per plan 14's change-binding behavior), `IMPLEMENTATION` because it writes the target repository's source files - and each is retry-eligible *only* as an explicit manual action gated by a required `--acknowledge-partial-changes` flag passed to the retry command: calling `retryStage`/`flow-retry` against a workflow `PAUSED` after a `CHANGE_PROPOSAL` or `IMPLEMENTATION` technical failure without that flag SHALL be rejected (no state change, no budget consumed - see D6); passing the flag SHALL be required and, when present, allowed to proceed through the same budget check as any other eligible stage. The orchestrator SHALL NOT ever re-run a write stage automatically, as a technical-failure retry or as a side effect of any other command; the flag only unlocks the explicit, single-call manual retry action itself. This prohibition is scoped to the technical-failure retry mechanism: it does not apply to, and does not forbid, the orchestrator's pre-existing content-correction loop inside `advance()` (`REVIEW`'s `CHANGES_REQUIRED` routing back to `IMPLEMENTATION`, or a revision request routing back to `CHANGE_PROPOSAL`), which re-runs a write stage as its own normal, budgeted control flow for a validly-executed stage reporting a content problem - a different mechanism from `retryStage`, governed by the content-correction budget (D8) instead of the technical-retry budget, and not gated by `--acknowledge-partial-changes` because the prior attempt did not fail technically or leave the repository in an unknown partial state.
Alternative considered (carried over from the original design before this correction): hardcode `IMPLEMENTATION` as never retryable at all, full stop, and treat `CHANGE_PROPOSAL` as a non-write, no-flag-required stage. Superseded - the corrected instructions require a manual, explicitly-acknowledged path to exist for `IMPLEMENTATION`, and `CHANGE_PROPOSAL` is correctly classified as a write stage subject to the same acknowledgement requirement, since it mutates on-disk change artifacts exactly as `IMPLEMENTATION` mutates target-repository source; the safety property is preserved by requiring informed, explicit human acknowledgement at the moment of retry instead of a blanket exclusion or an inconsistent exemption.

**D6: Invalid acknowledgement requests do not consume retry budget.**
A `retryStage`/`flow-retry` call rejected because required acknowledgement is missing (D5, write stage without `--acknowledge-partial-changes`), because the workflow is not currently `PAUSED` (or the specific `NOT_CONFIGURED` `AWAITING_USER` pause), because the workflow is terminal, or because the stage is not retry-eligible at all SHALL throw and leave the workflow's state - including both budget counters - unchanged. Only an attempt that is actually accepted and dispatched (the stage re-runs) counts against the technical-retry budget, win or lose. This applies symmetrically to D2: the counter increments when a real attempt is recorded (success, technical failure, or content correction), never when a call is rejected before any attempt runs.

**D7: `NOT_CONFIGURED` continues to pause at `AWAITING_USER`; `INFRASTRUCTURE_ERROR` is reclassified to pause at `PAUSED` under the technical-retry budget instead. Both use the same general `retryStage`/`flow-retry` command - no second command, no behavior-path duplication, and plan 13's actual config-reload mechanics are preserved untouched for the `NOT_CONFIGURED` case.**
Plan 13 pauses `VERIFICATION` at `AWAITING_USER` for both `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` (per plan 13's own design, since plan 13 predates `PAUSED` and had only `AWAITING_USER` available). This change does not change `NOT_CONFIGURED`'s routing: it does not introduce a new status for that case and does not duplicate plan 13's reload mechanism - `retryStage`/`flow-retry`, called against a workflow `AWAITING_USER` at `VERIFICATION` with `NOT_CONFIGURED` as its most recent outcome, SHALL re-invoke exactly plan 13's existing reload-and-recheck path internally (calling into whatever plan 13 implemented for this purpose) and then re-enter `advance(workflow)`, rather than this change reimplementing or re-deriving configuration reload logic itself. `INFRASTRUCTURE_ERROR`, however, now that `PAUSED` and the technical-retry budget both exist, is reclassified by this change (see the `workflow-orchestration` spec delta's MODIFIED "Unconfigured or broken verification configuration..." requirement) as a technical failure of `VERIFICATION`: it pauses at `PAUSED`, not `AWAITING_USER`, consumes the `VERIFICATION` stage's technical-retry counter exactly like any other technical failure, and reaches `FAILED` on budget exhaustion rather than remaining indefinitely `AWAITING_USER` with no budget. `retryStage`/`flow-retry` against a `PAUSED` workflow at `VERIFICATION` with `INFRASTRUCTURE_ERROR` as its most recent outcome follows the ordinary technical-retry path (task 7's budget/counter logic), not plan 13's `NOT_CONFIGURED`-specific reload-and-recheck branch - though the verifier itself still re-reads the configuration file fresh on that retry per plan 13's unchanged fresh-read requirement, so a corrected configuration file (not just a corrected executable/working-directory/timeout) is picked up either way. Any `retryVerification`-shaped method plan 13 added to `WorkflowEngine` is removed as part of this change and its single caller (`FlowCommands`) is updated to call `retryStage`/`flow-retry` instead - one general command replaces the narrow one, with plan 13's underlying reload behavior reused unchanged for `NOT_CONFIGURED`.
Alternative considered: keep `retryVerification` as a second, parallel command alongside `retryStage` for this one case. Rejected - the instructions explicitly require generalizing the existing command with no duplicate API; two coexisting retry entry points for overlapping purposes is exactly the inconsistency being corrected. Alternative considered: leave `INFRASTRUCTURE_ERROR` pausing at `AWAITING_USER` alongside `NOT_CONFIGURED`, unchanged from plan 13. Rejected - once `PAUSED` and a technical-retry budget exist, leaving `INFRASTRUCTURE_ERROR` at an unbounded `AWAITING_USER` pause is inconsistent with this change's own definition of a technical failure (D1/D2) and would let a persistently broken verification environment (e.g. a consistently missing executable) sit forever in a pause with no budget-driven path to `FAILED`, unlike every other technical failure this change introduces.

**D8: Budgets are two independent counters on `Workflow`, backed by `RetryProperties`, replacing `MAX_ADVANCE_STEPS` entirely; defaults are 3 technical retries per stage-attempt-sequence and 5 content-correction loops per workflow.**
Add `RetryProperties` (`@ConfigurationProperties(prefix = "pi-flow.retry")`) with `int maxTechnicalRetries` (default `3`) and `int maxContentCorrections` (default `5`), following the `AgentProperties`/`PiProperties` pattern. `Workflow` gains a per-current-stage-attempt-sequence technical-retry counter (reset to zero when the workflow moves to a new stage via a successful outcome - a fresh stage starts a fresh attempt sequence) and a per-workflow content-correction counter (never reset - scoped "per workflow" as the proposal states). `WorkflowEngineImpl.advance()` no longer uses `MAX_ADVANCE_STEPS` for budget purposes; the two configured budgets are the sole product-facing limits. A much larger, purely defensive infinite-loop safety net may remain internally but is never what either budget's test scenarios exercise, and is not reachable under correct configuration and correct dependency behavior.
Alternative considered: a single combined counter for both kinds. Rejected - the proposal requires independent, separately configurable budgets, since a technical retry (infrastructure/agent reliability signal) and a content-correction loop (expected iterative work) are different operational signals whose limits would be meaningless if conflated.

**D9: Auto-retry is disabled by default with no enabling configuration added by this change; only the manual `retryStage`/`flow-retry` command exists.**
No configuration property to enable unattended/automatic retry is introduced. The orchestrator's only paths that re-run a stage are: (a) the pre-existing content-correction loop inside `advance()` itself (unchanged in kind, now explicitly budgeted and classified per D4/D8), and (b) the explicit, manually-invoked `retryStage`/`flow-retry` command (D2, D5). No code path re-invokes a technically-failed stage without an explicit command call.
Alternative considered: add a configuration flag (e.g. `pi-flow.retry.auto-retry-technical-failures`) for operators who want unattended retry. Rejected for this change - the instructions state auto-retry is disabled by default and manual-only is "acceptable explicit"; introducing an auto-retry toggle at all is out of scope here and would need its own proposal with its own safety analysis (especially for write stages).

## Risks / Trade-offs

- [Risk] Allowing `CHANGE_PROPOSAL` or `IMPLEMENTATION` to be manually retried behind `--acknowledge-partial-changes` (D5) reopens a hazard the original design excluded outright (re-running a stage that may have left its artifacts - OpenSpec change files or target-repository source - partially modified) → Mitigation: the flag is mandatory and specific to this one action (not a global setting), so a human must make an informed, explicit, per-call decision at the moment of retry; the orchestrator performs no automatic rollback, resume-detection, or idempotency check of its own - the operator's acknowledgement is the entire safety mechanism, which is a deliberate, narrower trade-off than full automatic safety, consistent with the corrected instructions.
- [Risk] Splitting verifier failures into "content correction" (nonzero exit) vs. "technical pause" (process-start/timeout failure) depends on plan 13's `VerificationResult`/report shape actually exposing enough detail (exit code presence vs. absence, a timeout flag) to make the distinction reliably → Mitigation: this is a hard dependency on plan 13's landed shape, consistent with the Context's strict-ordering requirement; if plan 13's report does not yet expose a clear "did the process start/complete" signal, that is a plan 13 gap to fix in plan 13, not something this change should route around with a heuristic.
- [Risk] Resetting the technical-retry counter on every successful stage transition (D8) allows unbounded *total* technical retries across a long workflow that fails technically at a new stage each time → Mitigation: unchanged from the original design's accepted trade-off - the proposal scopes the budget "per stage-attempt-sequence," and the full attempt history (D3) remains inspectable so a human can observe and act on a workflow that keeps technically failing across different stages.
- [Risk] Introducing `PAUSED` as a sixth status is a breaking change to every exhaustive `switch` over `WorkflowStatus` and every caller that assumes exactly five values (e.g. shell output formatting, any persisted/serialized representation) → Mitigation: this is treated as an explicit, accepted breaking change scoped to this plan (consistent with plans 10/13/14 each already taking breaking changes when the behavior required it); tasks.md includes a task to grep and update every exhaustive switch/enum-set over `WorkflowStatus`.
