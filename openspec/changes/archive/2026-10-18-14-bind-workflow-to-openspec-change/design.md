# Design

## Context

See proposal.md - Why. Current state, read from `WorkflowEngine`, `WorkflowEngineImpl`, `Workflow`, `WorkflowStage`, `FlowCommands`, and the project's own `openspec/` layout:

- `WorkflowEngine.start(String task, String targetRepo)` takes two free-text strings; `WorkflowEngineImpl.start(...)` does not inspect `targetRepo` beyond storing it, and never reads `openspec/changes/` in that path.
- `WorkflowStage` orders `TASK_SETUP -> PROJECT_ANALYSIS -> CHANGE_PROPOSAL -> VALIDATION_APPROVAL -> IMPLEMENTATION -> VERIFICATION -> REVIEW -> ACCEPTANCE -> COMPLETED`. No OpenSpec change exists in the target repository until `CHANGE_PROPOSAL` runs and the architect agent creates one; this rules out any design that treats a change identifier as a `start(...)` precondition.
- `Workflow` stores `task`, `targetRepo`, `currentStage`, `status`, and `outcomes`; it has no field for a bound change identifier or any kind of fingerprint.
- `WorkflowEngineImpl.advance()`'s `CHANGE_PROPOSAL` case today is folded into the generic `PROJECT_ANALYSIS, CHANGE_PROPOSAL, IMPLEMENTATION, REVIEW` arm: it runs `stageRunner.run(stage, workflow)` and moves to `next(stage)` on success, with no stage-specific post-processing. `VALIDATION_APPROVAL`'s case only calls `workflow.markAwaitingUser()`; `approve(id)` moves the workflow straight to `IMPLEMENTATION` and calls `advance(workflow)`, with no intervening check.
- The project's own planning artifacts live under `openspec/changes/<name>/` with `proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`; `openspec validate <name> --strict` is the existing CLI entry point for deterministic structural validation (used already in plans 12's and 13's own tasks.md as a verification step). `openspec status --json`/equivalent list commands are the existing CLI entry points this project's own `.pi/skills/openspec-*` workflows already use to resolve a change by name rather than scanning the filesystem directly, which also naturally excludes `archive/` and anything outside the recognized change store.
- No code in the project currently shells out to `git` or to the `openspec` CLI from `src/main/java`; `JsonModePiRunner` is the only existing example of running an external process (`ProcessBuilder`, timeout, destroy-on-timeout, reader threads).
- Plan 12 (`stage-context-propagation`/`review-verdict`, see its design.md D3-D4) already establishes the pattern of a stage producing a structured, parseable result beyond a boolean (`ReviewVerdict` parsed from `REVIEW`'s agent output) and of `StageOutcome` carrying an optional typed payload alongside `success`/`output`. This change reuses that same shape for `CHANGE_PROPOSAL`'s change-identifier result instead of inventing a second mechanism.
- `FlowCommands.start(...)` passes its two shell arguments straight through to `engine.start(...)`.

## Goals / Non-Goals

**Goals:**
- Run a canonical-worktree-root Git check (via `git rev-parse`) before any agent stage invokes Pi, with no new mandatory `start(...)` argument.
- Let `CHANGE_PROPOSAL` be the sole place a change identifier is established, via a structured agent result, resolved against the OpenSpec CLI's view of active changes (not a raw directory scan), rejecting missing/ambiguous/path-escaping identifiers before any later-stage agent call.
- Bind a workflow to the first successfully resolved change identifier, permanently, and keep every later stage (including a `CHANGE_PROPOSAL` revision) referencing that same identifier.
- Run deterministic strict validation after binding and before the `VALIDATION_APPROVAL` gate is presented - not before `CHANGE_PROPOSAL`, since no change exists yet at that point.
- Capture an artifact fingerprint when the gate opens, and recheck it both before recording an approval and before implementation runs, reopening the gate (with revalidation) on any mismatch rather than ever recording an approval silently against drifted content.
- Define the fingerprinted file set deterministically, explicitly exempting `tasks.md` checkbox-only edits so a developer checking off tasks during/after approval does not force re-approval.
- Make zero Git write operations anywhere in this change's checks; accept a dirty worktree and an empty/uncommitted repository.
- Prefer implementing plans 10-13 before this one (dependency order 10, 11, 12, 13, then 14), reconciling additively rather than overriding their requirement text where it overlaps.

**Non-Goals:**
- Enforcing that `IMPLEMENTATION`'s actual code changes stay in scope of the approved proposal.
- Supporting a non-repo-local OpenSpec store/registry layout.
- Running `openspec validate` on every `advance()` call indefinitely; it runs once per binding/re-binding-confirmation (i.e. once per successful `CHANGE_PROPOSAL` resolution), not on every stage transition. The fingerprint recheck at approval/implementation time is a content-digest comparison, not a second `openspec validate` invocation - revalidation (an actual `openspec validate` run) only happens again if a fingerprint mismatch is detected and the gate reopens.
- A general-purpose retry/resume mechanism beyond "the user re-approves" or "the architect reruns `CHANGE_PROPOSAL`" - broader manual retry UX is plan 15's scope.
- Changing `Workflow`'s persistence technology.

## Decisions

**D1: `start(...)` keeps its existing two-argument signature; no change identifier is ever supplied by the caller.**
`WorkflowEngine.start(String task, String targetRepo)` is unchanged. This directly fixes the prior design's error: it required a change identifier as a `start(...)` precondition, which is impossible to satisfy for the documented "flow-start against a fresh/empty repository" scenario, since the change is `CHANGE_PROPOSAL`'s own output. There is no alternative considered here beyond the one being corrected; the signature does not change.

**D2: Repository preflight uses `git rev-parse` to resolve a canonical worktree root, not a `.git`-shape filesystem check.**
A new `GitWorktreeCheck` (or similarly named) component in `workflow.infrastructure` runs `git -C <targetRepo> rev-parse --show-toplevel` (or `--git-common-dir`/`--git-dir`, whichever combination unambiguously confirms "inside a worktree" while also correctly accepting a linked worktree, decided at implementation time by reading `git-worktree`'s documented output shape) as a bounded child process, reusing the timeout/destroy-on-timeout pattern from `JsonModePiRunner`. Exit code 0 means the path is inside a worktree; nonzero means it is not. This runs once, before `PROJECT_ANALYSIS` (the first stage that invokes Pi), as part of `start(...)`. Alternative considered: a bare filesystem check for a `.git` directory/file (the prior design's approach). Rejected per the proposal's correction - a bare shape check does not reliably distinguish a canonical worktree root from, e.g., a path *inside* a repository (a subdirectory containing no `.git` itself) or correctly recognize a linked worktree's gitdir-pointer file contents without duplicating `git`'s own resolution logic; `git rev-parse` is the authoritative, already-available tool for this and the project already accepts an external-process dependency shape (`pi` CLI) of the same kind.

**D3: Change-identifier resolution is a two-step process: a structured agent result from `CHANGE_PROPOSAL`, then OpenSpec-CLI-backed confirmation - never a free-text match or a raw directory scan.**
`AgentStageRunner`'s `CHANGE_PROPOSAL` invocation (building on plan 12's structured-result pattern) requires the architect agent's run to report a `changeId` field in its structured result. After a technically successful run, a new `OpenSpecChangeResolver` (or similarly named) component in `workflow.infrastructure` confirms that `changeId` by invoking the OpenSpec CLI's own listing/status mechanism (e.g. `openspec status --json` or the project's equivalent "list active changes" entry point - the exact subcommand decided at implementation time by reading the installed `openspec` CLI's documented output) rather than scanning `<targetRepo>/openspec/changes/` directly. This resolver rejects: an identifier matching zero or more than one entry in the CLI's reported active-change list, and an identifier containing path-traversal segments (`..`) or an absolute path, before ever treating the identifier as filesystem-safe. Alternative considered (the prior design's approach): resolve by raw filesystem listing of `openspec/changes/` with exact-name matching, supplied as a caller argument. Rejected per the proposal's correction on two counts - the identifier cannot be a caller argument (D1), and a raw filesystem scan does not use the OpenSpec CLI's own notion of "active change" (which can differ from "every directory present," e.g. if OpenSpec itself recognizes additional structure, hidden/draft states, or future store layouts); delegating resolution to the CLI keeps this change aligned with whatever the `openspec` tool itself considers canonical, consistent with D3 in the original design's reasoning for validation (not re-implementing OpenSpec's own rules in Java).

**D4: Binding happens on first successful resolution; later `CHANGE_PROPOSAL` runs (revisions) must confirm the same identifier, not supply a new one.**
`Workflow` gains `private String changeId` (null/absent until the first successful resolution, then immutable - no setter after first assignment; attempting to assign a second, different value SHALL throw `IllegalStateException`, surfaced by the engine as a failed `CHANGE_PROPOSAL` outcome rather than propagating a raw exception to the caller). `WorkflowEngineImpl`'s `CHANGE_PROPOSAL` handling: if `workflow.getChangeId()` is absent, bind to the newly resolved identifier; if already bound, require the newly resolved identifier to equal the bound one, else fail the stage. This directly implements the proposal's "revision stays bound to the same change" requirement and prevents an architect agent from silently proposing a second, unrelated change mid-workflow. Alternative considered: allow rebinding on every `CHANGE_PROPOSAL` success, trusting the architect to always report the same identifier it was told to revise. Rejected - trusting agent output without a hard check reintroduces exactly the "ambiguous/unchecked binding" risk the proposal is correcting; an explicit immutability check fails closed instead.

**D5: Strict validation runs once per successful binding/re-binding-confirmation, immediately after resolution and before the `VALIDATION_APPROVAL` gate opens - not before `CHANGE_PROPOSAL`, and not on every `advance()` call.**
A new `OpenSpecChangeValidator` (or similarly named) component in `workflow.infrastructure` runs `openspec validate <changeId> --strict` with working directory `targetRepo`, as a bounded child process (same timeout/destroy pattern), mapping exit code 0 to pass and nonzero to fail with captured output as the failure reason. `WorkflowEngineImpl`'s `CHANGE_PROPOSAL` success path, after D3/D4's resolution/binding succeeds, runs this validator before transitioning to `VALIDATION_APPROVAL`; a validation failure is recorded as a failed `CHANGE_PROPOSAL` outcome (naming the validator's captured output) and the workflow stays at/returns to `CHANGE_PROPOSAL` instead of advancing. This corrects the prior design's ordering error (which ran validation as a `start(...)`-time precondition, before any change could possibly exist). Alternative considered: validate on every entry into `VALIDATION_APPROVAL`, including after a fingerprint-triggered reopening. Accepted as part of this decision, not rejected - see D7, since reopening the gate due to drift is defined to re-run this same validation step, keeping "validation always precedes gate presentation" true unconditionally rather than only on the first pass.

**D6: The artifact fingerprint is a content digest (e.g. SHA-256) over a deterministic file set, computed with `tasks.md` checkbox markers normalized before digesting.**
A fingerprint utility reads, in sorted relative-path order: `proposal.md`, `design.md`, every file under `specs/`, and `tasks.md` with every occurrence of the checkbox markers `- [ ]` and `- [x]` rewritten to a single fixed placeholder (e.g. `- [_]`) before its bytes are included in the digest input; the digest is computed over path+normalized-content pairs (to also catch additions/removals, not just edits). This is computed at three points, all using the identical function: (a) when `VALIDATION_APPROVAL` is first presented after a successful binding/validation, recorded as the "gate fingerprint"; (b) inside `approve(id)`, before recording the approval, recomputed and compared against the current gate fingerprint; (c) immediately before `IMPLEMENTATION` runs, recomputed and compared against the fingerprint recorded at the most recent successful approval. `Workflow` stores a single `approvalFingerprint` field that is overwritten at (a) every time the gate opens and again at (b) when an approval is successfully recorded (so (c) always compares against the fingerprint as of the actual recorded approval, not the original gate-open moment, in case the user approved on a later presentation of the gate after a prior drift-triggered reopen). Alternative considered: exclude `tasks.md` entirely from the digest rather than normalizing its checkbox markers. Rejected - the proposal requires that non-checkbox edits to `tasks.md` (e.g. rewriting a task's instructions) still count as drift, since that is a real change to the approved plan; only the checkbox toggle itself is exempted, which normalization achieves while still covering the rest of the file's content.

**D7: A fingerprint mismatch (at approval time or at implementation time) triggers revalidation and reopens the `VALIDATION_APPROVAL` gate with a fresh fingerprint - it does not mark the workflow failed.**
On a mismatch detected in `approve(id)`: the approval is not recorded, the orchestrator re-runs `openspec validate <changeId> --strict` against the current artifacts (reusing D5's validator), and if validation still passes, re-presents the gate by recomputing and recording a fresh gate fingerprint (per D6(a)) and calling `workflow.markAwaitingUser()` again at `VALIDATION_APPROVAL`; if validation now fails, the outcome is recorded as a failed check and the workflow returns to `CHANGE_PROPOSAL` (mirroring D5's normal validation-failure routing). On a mismatch detected before `IMPLEMENTATION` (including after a resumed workflow), the same revalidate-and-reopen sequence runs, and `workflow.moveTo(WorkflowStage.VALIDATION_APPROVAL)` is called if the workflow had already moved past it. Every mismatch is recorded as a `StageOutcome` naming the detected drift so `WorkflowView.outcomes()` explains why the gate reopened. Alternative considered: mark the workflow `FAILED` on drift, requiring a full restart. Rejected - drift is a recoverable, user-actionable condition (the user or architect can simply re-approve or re-propose), consistent with plan 10's terminal-state-immutability guarantees not being the right fit for a condition this routine.

**D8: Reconciling with plans 10-13; dependency order 10, 11, 12, 13 is the default implementation sequence for this change, not a precondition for planning it.**
This change's tasks.md is written against the current (plans 10-13 not yet implemented) shapes of `WorkflowEngineImpl`, `Workflow`, and `StageOutcome`, but implementation of this change SHALL follow plans 10, 11, 12, and 13 in that order where their artifacts are ready, per the project's stated dependency ordering, rather than falling back to implementing 14 first merely because 14 was planned concurrently. Specifically: plan 10's `requireAwaitingUserAt` guard composes with this change's gate-reopening in D7 (reopening the gate SHALL go through the same guarded transition machinery, not bypass it); plan 12's structured-result/`StageOutcome` payload pattern is reused directly for `CHANGE_PROPOSAL`'s `changeId` field (D3), so plan 12 SHALL land first or be implemented in the same pass as this change's `CHANGE_PROPOSAL` handling; plan 13's `VerificationResult`/`VERIFICATION` stage is untouched by this change and has no ordering dependency either way. tasks.md includes a boundary-check task to confirm the actually-encountered order at implementation time, consistent with plans 11-13's own "read the other plans" tasks.

## Risks / Trade-offs

- [Risk] Resolving `changeId` via the OpenSpec CLI (D3) depends on the installed `openspec` CLI exposing a stable, parseable "list/status of active changes" output → Mitigation: this already mirrors the project's existing dependency on `openspec validate`'s CLI contract (used by plans 12/13's own tasks.md), and a CLI invocation failure (unparseable output, command not found) is mapped to the same "resolution failed, no later-stage agent call" rejection path as a genuine zero/ambiguous match, not treated as a silent pass.
- [Risk] Normalizing `tasks.md` checkbox markers before digesting (D6) means a non-standard checkbox rendering (e.g. a tab instead of a space, or a different marker format than `- [ ]`/`- [x]`) would not be normalized and could be misdetected as drift → Mitigation: the project's existing `tasks.md` files (confirmed by reading plans 10-13's own tasks.md) consistently use the `- [ ] N.M ...` format, so this is scoped to that convention; a non-conforming line is still digested as literal content, which fails safe (treated as drift) rather than silently exempted.
- [Risk] Reopening the gate on drift (D7) means a long-paused workflow at `IMPLEMENTATION` whose change artifacts were edited externally will unexpectedly need re-approval → Mitigation: this is the proposal's explicit intent; the recorded outcome names the detected drift so the reopening is explained, not a silent stall.
- [Risk] Binding immutability (D4) means an architect agent that genuinely needs to abandon the first proposed change and start a materially different one mid-workflow has no path forward except failing `CHANGE_PROPOSAL` repeatedly → Mitigation: this is intentional fail-closed behavior; abandoning a bound change for an unrelated one is a new workflow's job (`flow-start` again), not a revision of the current one, consistent with "revisions stay bound to the same change" being a hard requirement, not a preference.

## Open Questions

- The exact OpenSpec CLI subcommand/flag used for D3's "list active changes" resolution (e.g. `openspec status --json`, `openspec list`, or another equivalent) is decided at implementation time by reading the installed CLI's actual documented commands and output shape; this does not change any requirement's observable behavior, only which process invocation D3's resolver issues.
- Whether a target repository using a registered OpenSpec store (instead of a repo-local `openspec/changes/` directory) should be supported by future change-binding resolution. Deferred, as in the prior design: this change scopes resolution to whatever the OpenSpec CLI reports for the repo-local layout, which is the only layout any current workflow run uses.

## Implementation Notes (recorded during implementation)

- **Plans 10–13 order/shape (task 8.1):** plans 10, 11, 12, and 13 were all already landed (archived) when this change was implemented. Plan 12's `StageOutcome` carried `verdict`/`findings`/`verificationStatus` as `Optional`-wrapped fields; this change therefore extended that existing shape by adding a seventh `Optional<String> changeId` field plus a `changeProposed(...)` factory, rather than introducing a parallel structured-result mechanism. Plan 10's `requireAwaitingUserAt` guard is reused unchanged for gate commands; plan 13's `Verifier`/`VerificationResult` contract is untouched.
- **Plan 15 overlap (task 8.2):** plan 15 (`15-add-controlled-stage-retry`) was planned but not landed when this change was implemented. Its `PAUSED` status and `retryStage` mechanism target technical-failure retry of stage execution, while this change's drift-triggered "revalidate and reopen the approval gate" behavior targets content drift at `VALIDATION_APPROVAL`/`IMPLEMENTATION`. The two do not define conflicting recovery actions for the same states as of this change: on a failed `CHANGE_PROPOSAL` binding/validation this change follows the pre-15 convention of marking the workflow `FAILED` (stage remains `CHANGE_PROPOSAL`), which plan 15 can later replace with its retry routing without editing this change's artifacts.
