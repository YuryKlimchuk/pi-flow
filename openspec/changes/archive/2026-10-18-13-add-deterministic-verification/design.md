# Design

## Context

See proposal.md - Why for the always-pass-placeholder and startup-bound-configuration gaps, and proposal.md - Depends on for the required implementation order. Current state, read from `Verifier`, `AlwaysPassVerifier`, `WorkflowEngineImpl`, `WorkflowStatus`, `WorkflowEngine`, and `JsonModePiRunner`:

- `Verifier.verify(Workflow)` returns `boolean`; `AlwaysPassVerifier` always returns `true`.
- `WorkflowEngineImpl.advance()`'s `VERIFICATION` case: `boolean pass = verifier.verify(workflow); workflow.recordOutcome(new StageOutcome(stage, pass, ...)); workflow.moveTo(pass ? REVIEW : IMPLEMENTATION);` - a pure two-way branch with no path for "could not evaluate."
- `WorkflowStatus` has five values (`IN_PROGRESS`, `AWAITING_USER`, `COMPLETED`, `CANCELLED`, `FAILED`). Plan 10 makes `COMPLETED`/`CANCELLED`/`FAILED` immutable to every gate command and to `advance()`, and the gate commands already require `status == AWAITING_USER` at the expected stage before acting (plan 10's `requireAwaitingUserAt` guard).
- `JsonModePiRunner` demonstrates the project's pattern for running a configured external command as a child process with a timeout: `ProcessBuilder`, a configured `Duration` timeout via `process.waitFor(timeout, unit)`, `destroyForcibly()` on timeout, and daemon reader threads joined before returning. This change's command runner reuses that pattern but is a distinct, simpler implementation (no JSONL parsing, no agent resolution, no temp files).
- `AgentProperties`/`PiProperties` are both `@ConfigurationProperties` records bound once at JVM startup under `pi-flow.*` prefixes. This is the established pattern for settings that legitimately do not need to change without a restart (which command to run `pi` with). It is explicitly the *wrong* pattern for verification's command/timeout/working-directory configuration, because that configuration must be fixable by a user while a workflow is paused and waiting, in the same running process - see "Decisions" D2 below for why this change deliberately does not reuse the `@ConfigurationProperties` pattern for that part.
- `WorkflowEngine`'s five methods (`start`, `status`, `approve`, `reject`, `requestRevisions`, `requestFurtherWork`) are the only entry points into the engine from `FlowCommands` as of plan 10-12; there is no existing "retry" or "resume" method anywhere in the port yet. Plan 15 is expected to add a single general `retryStage(WorkflowId)` method; this change introduces the one, specific recovery action `VERIFICATION`'s pause needs, named and shaped so plan 15 can adopt or wrap it directly rather than redesigning it (see D5).
- This design is written against plan 10, plan 11, and plan 12 already being implemented: `Workflow`'s stage/status guard, the hardened `PiRunResult` contract, and `StageOutcome`'s `Optional<ReviewVerdict> verdict` / `Optional<List<String>> findings` fields are assumed present and are extended, not redesigned or reconstructed, by this change.

## Goals / Non-Goals

**Goals:**
- Replace the boolean `Verifier` contract with a four-valued `VerificationResult` (`PASSED`/`FAILED`/`NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR`) plus a bounded, truncation-flagged report.
- Provide a configurable, project-agnostic external-command verification check (argv, working directory override, timeout) with no assumed build tool, configured through a per-target-repository file that is re-read fresh on every verification attempt - never through a Spring-bound property that would require a process restart to change.
- Distinguish a command that ran and reported a problem (`FAILED`) from a command that could not be run at all (`INFRASTRUCTURE_ERROR`), and distinguish both from no configuration existing yet (`NOT_CONFIGURED`).
- Route `PASSED`/`FAILED` exactly as today's `true`/`false` did; add explicit, non-terminal, recoverable handling for `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` that does not silently pass, silently fail, or produce an unrecoverable stuck workflow, reconciling with plan 10's terminal-immutability guarantee.
- Define the recovery action's contract (what it requires, what it does, what it returns) precisely enough that plan 15 can generalize it into a cross-stage mechanism without needing to redesign this change's behavior.
- Keep the change scoped to the `Verifier` port, its new implementation, the `VERIFICATION` branch of `advance()`, and the minimal `WorkflowEngine` surface needed for a configuration-fix retry.

**Non-Goals:**
- Building the full general, cross-stage, user-initiated retry mechanism (plan 15's scope, explicitly deferred in the proposal). This change adds only the one specific recovery action `VERIFICATION`'s pause needs; it does not add a general `retryStage` covering other stages.
- Binding `IMPLEMENTATION` to the exact approved change (plan 14's scope).
- Assuming or defaulting to any specific build tool, test runner, or command. Every command this change runs is explicit user configuration, read from the per-target-repository file; no code path falls back to invoking a guessed command (e.g. `mvn verify`) when none is configured.
- Accepting a command, timeout, or working directory supplied by an agent/model, or embedded anywhere in agent output. The verification configuration file is read only from a fixed, user-controlled location on disk; nothing produced by `AgentStageRunner`/the Pi CLI is ever interpreted as, or merged into, verification configuration.
- Structured per-check results (e.g. separate lint/test/build sub-results). This change's `VerificationResult` wraps exactly one configured command's outcome.
- Changing `StageRunner`/`AgentStageRunner` or anything in the `agent-invocation` capability.

## Decisions

**D1: `Verifier` becomes `VerificationResult verify(Workflow)`, where `VerificationResult` is a new record in `workflow.application`.**
`record VerificationResult(VerificationStatus status, String report, boolean truncated)` with `VerificationStatus` as a new enum (`PASSED`, `FAILED`, `NOT_CONFIGURED`, `INFRASTRUCTURE_ERROR`) in the same package. Factory methods `VerificationResult.passed(report, truncated)`, `.failed(report, truncated)`, `.notConfigured(String reason)`, `.infrastructureError(String reason)` (both `reason`-based factories default `report` to the reason text and `truncated` to `false`, since there is no command output to truncate in either case). `failed(...)` is used only when the configured command actually started and completed within its timeout with a nonzero exit code; a timeout - the command started but did not complete in time, so its exit code was never observed - uses `infrastructureError(...)` instead, exactly like a failure to start the process at all, because both share the same distinguishing fact (the command's own exit behavior could not be observed). Alternative considered: collapse `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` into one "could not verify" status with a free-text reason. Rejected - the proposal requires the two to be distinguishable because they call for different user action: `NOT_CONFIGURED` means "add a configuration file," `INFRASTRUCTURE_ERROR` means "your existing configuration file or its referenced command/directory is broken," and collapsing them would force every caller to re-parse the reason text to tell those two apart.

**D2: Verification configuration is read from a per-target-repository JSON file, re-read fresh on every `verify(Workflow)` call, not bound once via `@ConfigurationProperties`.**
Add `VerificationProperties` (`@ConfigurationProperties(prefix = "pi-flow.verification")`) with exactly one field: `String configPath` (default `.pi-flow/verify.json`), interpreted as a path relative to the workflow's target repository root unless it is already absolute. This is the only verification setting bound at startup, and it configures *where to look for configuration*, not *what command to run* - changing it still requires a restart (consistent with every other `@ConfigurationProperties` path/location setting in the project, e.g. `PiProperties.command`), but that is an acceptable, rare operational change, unlike editing the command/timeout for a specific repository's checks, which must be a same-process, no-restart action per the proposal.
On every `verify(Workflow)` call, the new `Verifier` implementation resolves `configPath` against `workflow.getTargetRepo()` and reads the file fresh from disk (no caching across calls, no caching across retries): if the file does not exist, the result is `NOT_CONFIGURED`; if it exists but cannot be read (I/O error) or does not parse as the fixed schema below, the result is `INFRASTRUCTURE_ERROR` naming the specific problem (not found vs. unreadable vs. malformed JSON vs. schema violation are each named distinctly in the reason text, though all map to the same `INFRASTRUCTURE_ERROR` status). The fixed schema: a JSON object with `command` (array of strings, non-empty - an empty array is a schema violation, not an empty/absent configuration, since the file's mere existence already signals "configured"), `timeoutSeconds` (positive integer), and optional `workingDirectory` (string; when absent, defaults to `workflow.getTargetRepo()`). No other top-level keys are rejected (forward-compatible), but all three named keys SHALL be validated as specified; a missing `command` or `timeoutSeconds`, or a `timeoutSeconds` that is not a positive integer, or a `command` that is present but empty, is a schema violation -> `INFRASTRUCTURE_ERROR`.
Alternative considered: keep the whole configuration (command, timeout, working directory) in `VerificationProperties`/`application.yaml`, as the original design for this change proposed. Rejected per the proposal's explicit requirement that a paused-for-configuration workflow be recoverable by a user acting *within the same running process* - a Spring-bound property requires a JVM restart to change, which would discard every other workflow currently held in the in-memory `WorkflowRepository`, an unacceptable blast radius for fixing one workflow's verification configuration. Alternative considered: cache the file's parsed contents after the first successful read, re-reading only on an explicit cache-invalidation signal. Rejected - the proposal and the retry contract (D4) require that the *next* verification attempt (specifically, the one triggered by a user-initiated retry after they fixed the file) observes the fix; introducing a cache invalidation mechanism adds complexity to solve a problem ("avoid re-reading a small JSON file") that does not exist at this project's scale, and a stale cache would silently defeat the entire point of this decision.

**D3: Output capture bounds memory and report size by reading into a fixed-capacity buffer, not by reading everything then truncating.**
The command-running `Verifier` reads the child process's combined stdout+stderr (merged via `ProcessBuilder.redirectErrorStream(true)`) into a `StringBuilder` capped at a fixed `maxReportChars` constant (not configurable in this change - a build-time constant is sufficient since no proposal requirement asks for it to be tunable; documented in the implementing class's Javadoc). Once the cap is reached, further reads are drained (to avoid blocking the process on a full pipe) but discarded, and `truncated` is set `true`. Alternative considered: make the report-size bound configurable via `VerificationProperties`. Rejected for this change - the proposal's only required same-process-reconfigurable setting is the command/timeout/working-directory triple (D2); a fixed, generous constant (e.g. 20000 characters) satisfies "a pathological command cannot produce an unbounded report" without adding a second configuration surface this change does not otherwise need.

**D4: Both `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` pause the workflow in `AWAITING_USER` status at the `VERIFICATION` stage - no new `WorkflowStatus` enum value is added - recovered by a new `WorkflowEngine.retryVerification(WorkflowId)` method that re-enters `advance()` from that paused state.**
When `advance()`'s `VERIFICATION` case receives `NOT_CONFIGURED` or `INFRASTRUCTURE_ERROR`, it records the outcome (via the existing `StageOutcome` recording, not a stage move) and calls `workflow.markAwaitingUser()` without changing `currentStage` away from `VERIFICATION` - mirroring exactly how `VALIDATION_APPROVAL`/`ACCEPTANCE` already pause the engine today, reusing `WorkflowStatus.AWAITING_USER`'s existing "paused, waiting on an external actor" semantics rather than inventing new status values for either cause. `WorkflowEngine` gains `WorkflowView retryVerification(WorkflowId id)`; `WorkflowEngineImpl.retryVerification(id)` requires (reusing plan 10's guard helper) `currentStage == VERIFICATION && status == AWAITING_USER`, then calls `markInProgress()` and `advance(workflow)`, which re-invokes `verifier.verify(workflow)` - and because D2 re-reads the configuration file fresh on every call, this re-invocation naturally picks up whatever the user fixed on disk since the last attempt, with no restart and no cache to invalidate. The new result (now possibly `PASSED`/`FAILED`, or still `NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` if the user has not actually fixed the file yet) is routed normally. Alternative considered: add a sixth `WorkflowStatus` value distinguishing a configuration pause from a user-approval pause. Rejected - plan 10's terminal-immutability guard is keyed off `AWAITING_USER` specifically; a human fixing configuration and calling retry fits `AWAITING_USER`'s existing meaning precisely, exactly as plan 10 and plan 13's original design already established for `NOT_CONFIGURED` alone, and extending the same reasoning to `INFRASTRUCTURE_ERROR` keeps one pause mechanism instead of two near-identical ones.

**D5: `retryVerification` is named and scoped so plan 15 can generalize it into `retryStage` without redesigning this change's behavior; this change does not pre-build plan 15's general mechanism.**
`retryVerification(WorkflowId id)`'s full contract - precondition (`currentStage == VERIFICATION && status == AWAITING_USER`), action (`markInProgress()` then re-run `advance(workflow)`, which re-invokes `verifier.verify(...)` against freshly-read configuration), and result (`WorkflowView` reflecting whatever the re-run routed to) - is specified completely in this change (D4) so that a later, more general retry mechanism (plan 15) has an unambiguous, already-tested single-stage case to generalize from or delegate to, rather than needing to infer this change's intended behavior from scratch. This change does not add a second, more general method; it adds exactly the one method `VERIFICATION`'s pause needs. Alternative considered: skip adding `retryVerification` now and leave `VERIFICATION`'s pause with no recovery action until plan 15 lands. Rejected - the proposal requires this change to leave no dead-end state; a `NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` pause with no way to retry would be exactly the "stuck and immutable with no way forward" outcome plan 10's terminal-immutability guarantee was designed to avoid producing elsewhere.

**D6: Verification stage outcome recording extends plan 12's already-landed `StageOutcome` shape with a `verificationStatus` field, populated only for `VERIFICATION`-stage outcomes.**
`advance()`'s `VERIFICATION` case maps `VerificationResult` to `StageOutcome` as follows, using `StageOutcome`'s plan-12 constructor (`stage`, `success`, `output`, `verdict`, `findings`) extended with one additional field `verificationStatus`: `PASSED` -> `success = true`; `FAILED` -> `success = false`; `NOT_CONFIGURED` -> `success = false`; `INFRASTRUCTURE_ERROR` -> `success = false`; in every case `verificationStatus = Optional.of(result.status())`, `verdict = Optional.empty()`, `findings = Optional.empty()` (verification never populates plan 12's review fields). Collapsing `NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` into a plain `success = false` the same way `FAILED` is represented is rejected on its own: `success()` alone cannot recover which of the three non-passing causes applied, which is exactly the information `advance()`'s routing (D4) and any later human inspection of `workflow.outcomes()` need; `verificationStatus` carries the precise four-valued fact that routing actually switches on, while `success()` stays a reasonable boolean approximation for code that only checks it. This task extends plan 12's `StageOutcome` directly, as a fourth-plus-fifth-field addition to an already-landed five-argument shape; it is not a redesign of `StageOutcome` and does not touch the `verdict`/`findings` fields plan 12 added.

## Risks / Trade-offs

- [Risk] Reading the configuration file from disk on every `verify(Workflow)` call (D2) adds a filesystem read to every verification attempt → Mitigation: a small JSON file read is negligible next to the cost of actually running the configured verification command (which this change already runs as a child process with a multi-second-plus timeout); no caching is introduced because the proposal's recovery-without-restart requirement depends on every attempt seeing the current file contents.
- [Risk] Reusing `AWAITING_USER` for both the `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` pauses (D4) means a generic "is this workflow waiting on me" check cannot distinguish a proposal-approval gate, a missing-configuration pause, or a broken-configuration pause without also checking `currentStage` and the most recent outcome's `verificationStatus` → Mitigation: every existing pause in the system already requires checking `(stage, status)` together; this is consistent with, not a regression from, the current design, and the recorded outcome's `verificationStatus` plus report text names the specific cause for any caller that needs to tell the two apart.
- [Risk] Capping output capture mid-read (D3) could truncate output in a way that cuts off a meaningful final line → Mitigation: the `truncated` flag is always set when this happens, so a report consumer is told the report is incomplete rather than trusting a silently-cut report.
- [Risk] A fixed, non-configurable report-size bound (D3) might be too small or too large for some future command's typical output → Mitigation: explicitly scoped as a Non-Goal for this change to make configurable; a future change can add a `VerificationProperties` field for it without altering this change's `VerificationResult`/schema contract.
- [Risk] `retryVerification` (D4/D5) is a stage-specific method that plan 15 is expected to generalize or replace → Mitigation: this is stated explicitly as the intended integration path (D5), not an accident; tasks.md includes a boundary-check task to confirm plan 15, once it exists, actually adopts or wraps this method's contract rather than introducing an incompatible parallel one.
- [Risk] Validating the configuration file's schema strictly (D2) means a user's small typo (e.g. `timeoutSeconds` as a JSON string `"30"` instead of a number) produces `INFRASTRUCTURE_ERROR` rather than a lenient coercion → Mitigation: this is intentional - silently coercing a malformed value could mask a real user mistake with surprising runtime behavior (e.g. a very different timeout than intended); the `INFRASTRUCTURE_ERROR` reason text names the specific schema violation so the fix is obvious, and the same-process retry (D4) means fixing a typo and retrying is cheap.
