# Proposal

## Why

`WorkflowEngineImpl.start(task, targetRepo)` and `advance()` only read `workflow.getTask()`/`workflow.getTargetRepo()` (confirmed by reading `AgentStageRunner.promptFor` and `WorkflowEngineImpl`); there is no requirement that `targetRepo` be a canonical Git worktree, and no deterministic link between a running workflow and a specific, identifiable OpenSpec change. The workflow's own stage ordering (`WorkflowStage`: `TASK_SETUP`, `PROJECT_ANALYSIS`, `CHANGE_PROPOSAL`, `VALIDATION_APPROVAL`, `IMPLEMENTATION`, ...) means no OpenSpec change exists yet when `start(...)` is called: the change is the *output* of the `CHANGE_PROPOSAL` stage, produced by the architect agent, not an input the caller can name in advance. A design that requires a change identifier as a `start(...)` precondition is incompatible with this project's own documented flow (`docs/workflow.md`) of starting a workflow against a fresh task and a repository that may not even have any `openspec/changes/` entries yet - including the common case of an empty/uninitialized Git repository with no OpenSpec changes at all.

Because `CHANGE_PROPOSAL` and `IMPLEMENTATION` currently run against whatever free-text `task` string was supplied, with no check that a produced proposal corresponds to a real `openspec/changes/<name>` directory, no deterministic validation that the directory's artifacts are internally valid (`openspec validate --strict`), and no way to tell, after a user approves at `VALIDATION_APPROVAL`, whether the approved artifacts were later edited on disk before `IMPLEMENTATION` actually runs - the workflow cannot guarantee that what gets implemented is what was actually reviewed and validated. Running `IMPLEMENTATION` against drifted or never-validated artifacts wastes paid Pi invocations and can implement something the user never actually approved.

## What Changes

- Target repository preflight SHALL run before any agent stage (including `PROJECT_ANALYSIS`) invokes Pi for a workflow: the orchestrator SHALL resolve `targetRepo` to a canonical Git worktree root using `git rev-parse` (not a bare filesystem check of `.git`'s shape), accepting any valid worktree (main or linked) and rejecting a path that does not exist or is not inside a Git worktree. An existing Git repository with no commits yet SHALL be accepted. This preflight SHALL NOT perform any Git write operation (commit, reset, stash, checkout, clean), and a dirty worktree SHALL be accepted and left untouched.
- `WorkflowEngine.start(...)` SHALL NOT gain any new mandatory argument. No OpenSpec change exists at `start(...)` time; the change is created later by the `CHANGE_PROPOSAL` stage's architect agent, not supplied by the caller.
- The `CHANGE_PROPOSAL` stage's agent invocation SHALL be run in a mode that requires a structured result naming the exact OpenSpec change identifier (directory name) the architect created or revised, rather than free text alone. Immediately after a successful `CHANGE_PROPOSAL` run, the orchestrator SHALL resolve that identifier against the target repository's actually-present OpenSpec changes using the OpenSpec CLI (not a raw filesystem scan), and SHALL refuse to proceed - reporting the `CHANGE_PROPOSAL` stage as failed - if the identifier is missing, does not resolve to exactly one active change, or would resolve outside the target repository's OpenSpec change store (path escape, e.g. `..` segments or an absolute path pointing elsewhere). No agent call for a later stage runs for a workflow that fails this resolution.
- On the first successful resolution, the workflow SHALL bind permanently to that change identifier for the remainder of its lifetime; the bound identifier SHALL be recorded as part of the workflow's state. Immediately after binding, and before the `VALIDATION_APPROVAL` gate is presented to the user, the orchestrator SHALL run deterministic, local-only strict validation of the bound change's artifacts (equivalent to `openspec validate <changeId> --strict`, run as a bounded local process, not an agent call); a validation failure SHALL prevent the `VALIDATION_APPROVAL` gate from being presented and SHALL be recorded as the reason, routing back to `CHANGE_PROPOSAL` for correction rather than surfacing an unvalidated proposal to the user.
- When a workflow returns to `CHANGE_PROPOSAL` (via `requestRevisions()` or via validation failure above), it SHALL remain bound to the same change identifier already recorded; the revision run SHALL revise that same change and SHALL NOT rebind to a different identifier. If the architect's structured result on a revision run names a different change identifier than the one already bound, the orchestrator SHALL treat this as a `CHANGE_PROPOSAL` failure rather than silently rebinding.
- All later stage context (`IMPLEMENTATION`, `REVIEW`, and any other stage reached after binding) SHALL reference the one bound change identifier; no stage after binding SHALL re-resolve or re-derive a different change from free text.
- Introduce an **artifact fingerprint**: a deterministic digest computed over a defined, deterministic set of the bound change's files. The fingerprint SHALL be captured at the moment the proposal is presented to the user at the `VALIDATION_APPROVAL` gate (i.e. when the gate opens), not only at the moment of approval. On `approve()`, before recording the approval, the orchestrator SHALL recompute the digest and compare it to the captured gate fingerprint; a mismatch SHALL prevent the approval from being recorded, SHALL re-run strict validation against the current artifacts, and SHALL re-present (reopen) the `VALIDATION_APPROVAL` gate with a freshly captured fingerprint instead of silently recording approval against stale content. The same recompute-and-compare check SHALL run again immediately before `IMPLEMENTATION` executes (covering the gap between a recorded approval and a later-resumed workflow); a mismatch detected there SHALL block `IMPLEMENTATION`, trigger revalidation, and reopen the gate the same way.
- The fingerprint's file set SHALL be defined deterministically and SHALL exclude `tasks.md` checkbox state specifically: a change in which the only difference is a task checkbox being checked/unchecked (`- [ ]` <-> `- [x]`) SHALL NOT be treated as drift and SHALL NOT force re-approval. All other content (including non-checkbox edits to `tasks.md`, and all content of `proposal.md`, `design.md`, and every file under `specs/`) SHALL be covered by the fingerprint and SHALL be treated as drift when changed.
- The orchestrator SHALL NOT perform any Git write operation as part of repository preflight, change-identifier resolution, validation, or fingerprinting, at any point in this change.
- Add tests covering: canonical-worktree-root preflight (main worktree, linked worktree, non-repo path, non-existent path, empty/uncommitted repo), `start(...)` requiring no new argument, `CHANGE_PROPOSAL` producing a structured result with a change identifier, missing/ambiguous/path-escaping identifier rejected as a `CHANGE_PROPOSAL` failure with no later-stage agent call, binding recorded on first successful resolution, a revision run remaining bound to the same identifier (including the identifier-mismatch-on-revision failure case), strict validation blocking gate presentation before approval is possible, fingerprint captured at gate-open time, fingerprint re-checked and blocking at approve-time and at implementation-time, a tasks.md-only checkbox edit not triggering drift, and a dirty worktree being left unmodified throughout.

## Capabilities

### New Capabilities
- `change-binding`: defines canonical-worktree-root repository preflight before any agent call, how a workflow binds to the OpenSpec change identifier produced by the `CHANGE_PROPOSAL` stage's structured result, deterministic strict validation before the approval gate is presented, and the artifact fingerprint (captured at gate-open, rechecked at approval and at implementation) that detects drift while exempting `tasks.md` checkbox-only edits.

### Modified Capabilities
- `workflow-orchestration`: "Start workflow" gains the canonical-worktree-root preflight precondition (no new mandatory argument). "Change-proposal stage" gains the structured-result change-identifier requirement and binding-on-first-success behavior, with revisions staying bound to the same identifier. "Approval gate" gains fingerprint capture at gate-open, fingerprint verification before approval is recorded, and fingerprint verification before implementation proceeds.

## Impact

- `src/main/java/.../workflow/api/WorkflowEngine.java`: `start(...)` signature is unchanged (no new argument).
- `src/main/java/.../workflow/domain/Workflow.java`: gains storage for the bound change identifier (absent until `CHANGE_PROPOSAL` first succeeds, then immutable) and the recorded gate/approval fingerprint.
- `src/main/java/.../workflow/application/WorkflowEngineImpl.java`: `start(...)`/`advance()`'s pre-`PROJECT_ANALYSIS` step performs the canonical-worktree-root preflight; the `CHANGE_PROPOSAL` branch resolves and binds the change identifier from the structured agent result and runs strict validation before the `VALIDATION_APPROVAL` gate opens (capturing the gate fingerprint at that point); `approve(...)` re-verifies the fingerprint before recording approval; `advance()`'s `IMPLEMENTATION` entry re-checks the fingerprint before running the stage.
- `src/main/java/.../workflow/infrastructure/`: new component(s) for the canonical-worktree-root check (`git rev-parse`-based), resolving/confirming the bound change via the OpenSpec CLI, running `openspec validate --strict` as a local process, and computing the artifact fingerprint over the deterministic file set - concrete shape decided in design.md.
- `src/main/java/.../shell/FlowCommands.java`: `flow-start` shell command is unchanged (no new argument).
- Tests: new unit/fixture tests for worktree-root preflight, change-identifier resolution and binding, strict validation, and fingerprinting; `WorkflowEngineImplTest` gains cases for the `CHANGE_PROPOSAL`-stage binding/validation behavior and the approve-time/implementation-time fingerprint checks.
- No changes to `agent-invocation` capability's general contract, `StageRunner`/`AgentStageRunner`'s per-stage prompt-building logic beyond what plan 12 already introduced (this change reuses plan 12's structured-result pattern for the `CHANGE_PROPOSAL` stage's change-identifier field), or the `Verifier`/`VerificationResult` contract from plan 13.
- Depends on plans 10-13 being planned (their artifacts exist) and SHALL be reconciled against whichever of plans 10-13 has actually landed by the time 14 is implemented, following dependency order 10, 11, 12, 13 before 14 as the default implementation sequence; this is a sequencing preference for implementation, not a precondition that blocks this change's planning.

## Non-goals

- Enforcing that `IMPLEMENTATION`'s actual code changes stay within the scope of the approved proposal. This change only binds the workflow to one change directory and detects drift in that change's own artifact files; it does not inspect or constrain what `IMPLEMENTATION` subsequently writes elsewhere in the repository.
- Supporting a target repository that uses a registered OpenSpec store instead of a repo-local `openspec/changes/` directory layout.
- Choosing or changing `Workflow`'s persistence technology.
- A general-purpose manual retry/resume UX beyond "the user re-approves" or "the architect reruns `CHANGE_PROPOSAL`" - broader retry UX is plan 15's scope.
