# Design

## Context

See proposal.md - Why for the no-structured-history and log-leakage gaps. Current state, read from `WorkflowEngineImpl`, `Workflow`, `StageOutcome`, `JsonModePiRunner`, and plans 10-15's artifacts, as of this writing:

- None of plans 10-15 are implemented in `src/main/java` (confirmed by reading `StageOutcome` - still the original 3-field `(stage, success, output)` record with no `AttemptKind`/`ReviewVerdict`/`VerificationResult` field - `WorkflowEngineImpl.advance()` - still the single undifferentiated `MAX_ADVANCE_STEPS = 50` loop guard, no `retryStage` method - and the absence of `AttemptKind`, `RetryProperties`, `ReviewVerdict`, `VerificationResult`, or `VerificationProperties` anywhere in `src/main/java`). This change is sequenced to be implemented strictly after plans 10, 11, 12, 13, 14, and 15, in that numeric order. It is designed and specified against the shapes those plans define, not against a conditional "if present, else fall back" runtime check; there is no supported standalone or independent mode for this capability, and its tasks.md does not include a task for operating without those predecessors.
- Plan 15 is being updated concurrently with this change's own planning. Every reference in this design to plan 15's `AttemptKind`, `Workflow`'s attempt-history fields, `retryStage`, or `RetryProperties` is a reference to plan 15's artifacts as currently committed to disk (`openspec/changes/15-add-controlled-stage-retry/design.md` D1-D6, `specs/controlled-stage-retry/spec.md`), re-read at the time this change moves from planning to implementation. If plan 15's committed shape has changed by then, this design's D1-D2 below are re-validated against the new shape before task 1 of tasks.md is executed.
- `WorkflowEngineImpl.advance()` dispatches each stage, records a `StageOutcome` on `Workflow.outcomes()` (an append-only `List<StageOutcome>`), and separately calls `log.info`/`log.warn` for Pi runs (`JsonModePiRunner.runCommand`). Reading `JsonModePiRunner.runCommand` directly: its "Starting Pi run" `log.info` call interpolates `command` (the full `ProcessBuilder` argument list, whose last element is the raw agent prompt) verbatim; its "Pi run finished" `log.info` call interpolates `result.finalText()` through a display-only 200-character `truncate()` helper that is not a redaction - the full, untruncated `finalText` is still held in the returned `PiRunResult` and the truncated form itself is still the agent's real response text, just shortened. Both call sites are an existing, shipped leak this change is required to correct, not merely document.
- `AgentProperties`/`PiProperties` are the established `@ConfigurationProperties` pattern (`pi-flow.*` prefixes, defaults applied in a canonical constructor/record) this change follows for its own bounds configuration.
- `FlowCommands`/`AgentCommands` are the established `@CommandGroup` + `@Command`/`@Argument` shell command pattern this change follows for its new reporting command.
- `WorkflowRepository`'s only implementation (`InMemoryWorkflowRepository`) makes an in-memory-only diagnostics store the only viable shape for this change; this is a hard boundary stated in the proposal, not an open question.

## Goals / Non-Goals

**Goals:**
- Define one diagnostic-entry shape and one bounded, per-workflow diagnostics record that every stage attempt feeds, built strictly on top of plan 15's attempt-history fields (stage, attempt sequence number, `AttemptKind`) rather than recomputing or duplicating them.
- Make the safe-content exclusion (no prompt/response text, no secrets) structurally hard to violate: the reason-building code path should not have access to raw prompt/response strings or to secret-bearing configuration, not merely be reviewed to avoid using them.
- Correct `JsonModePiRunner`'s existing two log lines so neither the raw prompt/argv nor `finalText` is logged, as a required part of this change.
- Keep the mechanism purely additive to plan 15's workflow-orchestration logic: no change to `WorkflowEngine`'s method signatures, no change to `StageOutcome`'s fields beyond what plans 11-15 already define, and no change to any routing/transition logic in `WorkflowEngineImpl.advance()`.
- Establish an explicit, documented split between `Workflow.outcomes()` (full, unbounded, preserved history - plan 15's responsibility) and `WorkflowDiagnostics` (bounded, truncatable, derived reporting projection - this change's responsibility), so the two are never confused as interchangeable sources of truth.

**Non-Goals:**
- Persisting diagnostics beyond process memory, or shipping them to any external log/metrics/tracing system. This is a hardcoded exclusion per the proposal, not a configuration option.
- Replacing, restructuring, or truncating `Workflow.outcomes()`/`StageOutcome`; diagnostics is a parallel, bounded, derived record built from plan 15's attempt events, never a replacement for or alternate copy of the full outcome history.
- Introducing a general query/filter API over diagnostics (by category, by time range, by stage); the shell command renders the full retained (bounded) history for one workflow, nothing more granular.
- Capturing diagnostics for anything other than workflow stage attempts (e.g. `AgentCommands.piRun`'s standalone `pi-run` shell command is out of scope; it has no owning `Workflow`). That command's own logging is unaffected by this change except where it shares `JsonModePiRunner`'s corrected log lines.
- Defining a speculative, independent operating mode for when plans 10-15 are not implemented. This capability has exactly one supported precondition: plans 10-15 implemented first, in order.

## Decisions

**D1: `WorkflowDiagnostics` reads its attempt identity directly from plan 15's `Workflow`/`StageOutcome` attempt-history fields; it does not maintain its own attempt counter.**
`Workflow` gains a `WorkflowDiagnostics diagnostics()` accessor returning a bounded, append-only (drop-oldest-on-overflow) list of `DiagnosticEntry` records (`stage`, `attemptSequence`, `startedAt`, `duration`, `category`, `reason`, `reasonTruncated`). `WorkflowEngineImpl.advance()` (and plan 15's `retryStage`) times each stage dispatch (`Instant.now()` before/after `stageRunner.run(...)`/`verifier.verify(...)`) and, immediately after calling `workflow.recordOutcome(...)` (plan 15's call, which assigns/increments the real attempt sequence number and `AttemptKind`), reads that just-recorded `StageOutcome`'s attempt sequence number and kind back out and passes them into `workflow.recordDiagnostic(...)`. This change never increments its own sequence counter and never infers attempt identity independently. Alternative considered: give `WorkflowDiagnostics` its own attempt-sequence counter, incremented each time a diagnostic entry is recorded. Rejected - two independently incremented counters for "which attempt is this" is exactly the duplicate, divergent record-keeping the proposal requires this change to avoid; a diagnostics-local counter could drift from plan 15's real attempt sequence (e.g. if a future change adds an attempt-boundary that only one of the two call sites updates), which is a correctness risk with no corresponding benefit over reading the one number plan 15 already computes.

**D2: `DiagnosticCategory` is a dedicated enum local to this capability, mapped from plan 12's `ReviewVerdict`, plan 13's `VerificationResult`, and plan 15's `AttemptKind` - all three read as their actual implemented shapes, not reused directly as the diagnostics category.**
Define `DiagnosticCategory` (`SUCCESS`, `TECHNICAL_FAILURE`, `CONTENT_CORRECTION`, `TIMEOUT`, `NOT_CONFIGURED`) in the diagnostics package. `WorkflowEngineImpl`'s recording call site maps the stage outcome to exactly one category: a successful outcome -> `SUCCESS`; plan 15's `AttemptKind.CONTENT_CORRECTION` (`REVIEW`'s `CHANGES_REQUIRED` per plan 12, or verification's `FAILED` per plan 13) -> `CONTENT_CORRECTION`; a `PiRunResult`/`StageOutcome` indicating a timeout (plan 11's `PiRunStatus.TIMEOUT`) -> `TIMEOUT`; plan 13's `VerificationResult.NOT_CONFIGURED` -> `NOT_CONFIGURED`; every other technical/process failure (plan 15's `AttemptKind.TECHNICAL_RETRY` origin) -> `TECHNICAL_FAILURE`. This mapping is finalized against plans 11-13/15's actual implemented field names at the start of task 1 (boundary check), not left as a conditional branch evaluated at runtime. Alternative considered: reuse plan 15's `AttemptKind` directly as the diagnostics category. Rejected - `AttemptKind` (`INITIAL`/`TECHNICAL_RETRY`/`CONTENT_CORRECTION`) describes *why an attempt was made*, not *what happened in that attempt* (an `INITIAL` attempt can still fail technically or time out); conflating the two would make `SUCCESS` and `TIMEOUT` unrepresentable for a first attempt.

**D3: The reason string is built from an explicit allow-list of fields, never from a formatting method that has access to the full `StageOutcome`/`PiRunResult` object or to secret-bearing configuration.**
The recording call site passes a small, explicit set of primitive values into a `DiagnosticEntry` factory (stage name, category, an optional status/exit code, an optional existing diagnostic-text string already known to be process/protocol-scoped such as `PiRunResult.diagnostics()`) rather than passing the whole `StageOutcome`/`PiRunResult` object into a generic formatter. The factory's parameter list has no path to `finalText`, the stage's prompt, `workflow.getTask()`, or any `@ConfigurationProperties` object that could carry a credential/API key. This makes it structurally impossible for the reason-building code to accidentally interpolate prohibited content, since those values are never passed in. Alternative considered: pass the full `StageOutcome` into a `toReason()` method and trust that method's implementation (and its tests) to omit `output()`/`finalText`/secrets. Rejected - the proposal requires this exclusion to be a hard, verifiable property; restricting the factory's inputs makes the exclusion enforceable by the type signature and by a focused unit test asserting the factory method does not accept those fields, rather than by code review discipline alone.

**D4: Bounds are two independent configuration properties under `DiagnosticsProperties` (`@ConfigurationProperties(prefix = "pi-flow.diagnostics")`), with explicit defaults: `maxEntriesPerWorkflow` (default `200`) and `maxReasonLength` (default `500`).**
`WorkflowDiagnostics` enforces both bounds internally: appending beyond `maxEntriesPerWorkflow` drops the oldest entry and sets an internal `entriesDropped` flag (sticky once set); constructing a `DiagnosticEntry` whose computed reason exceeds `maxReasonLength` truncates it and sets `reasonTruncated` on that entry. Any raw stdout/stderr text read into a reason (via `PiRunResult.diagnostics()`, itself already drained by `JsonModePiRunner`'s existing non-blocking daemon reader threads) is subject to the same `maxReasonLength` cap - this change does not add a second, separate output-capture buffer or a blocking read; it only ever consumes the already-captured, already-bounded-at-the-source text that `PiRunResult` exposes. Alternative considered: a single combined "diagnostics buffer size in bytes" bound covering both entry count and reason length together. Rejected - the proposal calls for independently configurable caps for entry count and reason length, matching the project's existing pattern of distinct, purpose-named properties (e.g. plan 15's `maxTechnicalRetries`/`maxContentCorrections`) rather than one overloaded size budget that conflates two different failure modes.

**D5: The shell command is a new `@Command` in a dedicated `DiagnosticsCommands` class, not an addition to `FlowCommands`.**
Add `DiagnosticsCommands` (new `@CommandGroup`) with a single `flow-diagnostics <id>` command that resolves the workflow via the same `WorkflowRepository`/`WorkflowId` lookup pattern `WorkflowEngineImpl`/`FlowCommands` already use, and renders each retained `DiagnosticEntry` as one line (stage, attempt sequence, duration, category, reason), plus a trailing note if `entriesDropped` is set. An unknown workflow id reports "unknown workflow" text, mirroring `FlowCommands`' existing `IllegalStateException`-on-unknown-id convention. Note: `FlowCommands.status()`'s existing `render()` method today shows only `id`/`stage`/`status`/`lastOutput` - it does not show the workflow's task or target repository, and this change does not add that; `flow-diagnostics` is a separate, additive command and is not a replacement for or extension of `flow-status`'s rendering. Alternative considered: add `flow-diagnostics` directly to `FlowCommands`. Rejected - `FlowCommands` is scoped to workflow-state-mutating gate commands plus `flow-status`; a reporting-only command for a parallel, additive capability fits better as its own group.

**D6: `JsonModePiRunner`'s two existing `log.info` call sites in `runCommand` are corrected as part of this change, not deferred.**
The "Starting Pi run" log line is changed to log the executable name (`properties.command()`'s first token, or a fixed literal), the working directory, and the timeout - never the full `command` list and never the prompt. The "Pi run finished" log line is changed to log the exit code, `result.status()`, and `result.diagnostics()` - never `result.finalText()` in any form, truncated or not; the existing `truncate(...)` helper is removed from this log call entirely (truncation does not make logging final text safe, since the truncated text is still real response content). Alternative considered: keep `truncate(...)` but shorten it further (e.g. to 50 characters) as a compromise. Rejected - any non-empty fragment of the agent's real response is still agent response content, which the proposal's hard exclusion prohibits regardless of length; the correct fix is omission, not finer truncation.

## Risks / Trade-offs

- [Risk] D1's dependency on plan 15's attempt-history fields means this change cannot be implemented, or even fully designed at the field-name level, until plan 15 is actually implemented and its artifacts stop changing → Mitigation: this is accepted and stated explicitly as a hard precondition (not a soft preference) in proposal.md's Impact section; task 1 of tasks.md re-reads plan 15's committed shape immediately before implementation and halts if plan 15 is not yet implemented.
- [Risk] D2's category mapping depends on reading plans 11-13/15's actual implemented shapes at implementation time; a naming or shape change in any of them after this design is written requires updating the mapping table → Mitigation: tasks.md's boundary-check task (task 1) requires re-reading the actual files and updating the mapping before any other task proceeds, rather than assuming this design's field names are still accurate.
- [Risk] Dropping the oldest entries on overflow (D4) could hide the *earliest* failures in a long-running, heavily-retried workflow, which are sometimes more diagnostically interesting than the most recent ones → Mitigation: the `entriesDropped` flag makes the loss visible rather than silent; the full, untruncated history remains available via plan 15's `Workflow.outcomes()` regardless of what this capability's bounded projection has dropped, so no information is actually lost, only absent from the bounded report.
- [Risk] D6's log-line correction touches `JsonModePiRunner`, a class also exercised by `AgentCommands.piRun` and by existing `JsonModePiRunnerTest` assertions that may currently assert on logged content → Mitigation: tasks.md includes a task to grep existing tests for assertions on the corrected log lines' content before changing them, and to update any such assertion to match the corrected, safe log output rather than leaving a stale assertion that happens to still pass.
