# modular-architecture Specification

## Purpose
Задаёт базовую модульную архитектуру pi-flow: состав модулей, границы их ответственности, допустимые и запрещённые взаимодействия, направление зависимостей и ограничения модульности, пригодные для автоматической проверки средствами Spring Modulith.

## Requirements

### Requirement: Приложение строится как модульный монолит

Система SHALL быть организована как модульный монолит на Spring Modulith, где модули являются явно выделенными единицами с собственными границами ответственности.

#### Scenario: Явные модули

- **WHEN** рассматривается структура приложения
- **THEN** каждый модуль имеет однозначно определённую ответственность и явную границу, различаемую инструментами Spring Modulith

### Requirement: Состав базовых модулей

Система SHALL содержать следующие базовые модули: `workflow`, `workspace`, `agent`, `interaction`, `github` и `web`.

#### Scenario: Наличие модулей

- **WHEN** приложение собрано
- **THEN** каждый из модулей `workflow`, `workspace`, `agent`, `interaction`, `github`, `web` существует как отдельный Modulith-модуль

### Requirement: Модуль workflow координирует жизненный цикл процесса

Модуль `workflow` SHALL владеть моделью бизнес-процесса разработки (этапы, состояния, переходы) и координировать выполнение процесса, не выполняя локальные Git-операции, запуск Pi или вызовы GitHub API напрямую.

#### Scenario: Координация без инфраструктурных деталей

- **WHEN** workflow координирует процесс
- **THEN** он делегирует локальные Git-операции модулю `workspace`, запуск агентов — модулю `agent`, а операции GitHub — модулю `github`

### Requirement: Модуль workspace владеет локальными репозиториями и Git-операциями

Модуль `workspace` SHALL владеть локальными репозиториями, рабочими ветками, локальными Git-операциями и блокировками репозиториев, и НЕ должен выполнять операции GitHub API.

#### Scenario: Локальные операции отделены от GitHub API

- **WHEN** требуется операция с локальным репозиторием или веткой
- **THEN** она выполняется модулем `workspace`, а не модулем `github`

### Requirement: Модуль agent управляет запуском Pi-процессов

Модуль `agent` SHALL отвечать за запуск Pi-процессов в ролях Analyst, Architect, Developer и Reviewer, передачу им контекста и фиксацию технических сведений о выполнении, и НЕ должен содержать бизнес-правил workflow.

#### Scenario: Запуск ролей

- **WHEN** workflow требует выполнить роль (Analyst/Architect/Developer/Reviewer)
- **THEN** это выполняется через контракт модуля `agent`

### Requirement: Модуль interaction управляет взаимодействием с пользователем

Модуль `interaction` SHALL владеть вопросами к пользователю, ответами, подтверждениями и решениями, ожидающими участия пользователя, и НЕ должен управлять последовательностью этапов workflow.

#### Scenario: Контрольные точки

- **WHEN** процессу требуется ответ или подтверждение пользователя
- **THEN** он передаётся через контракт модуля `interaction`

### Requirement: Модуль github инкапсулирует GitHub API

Модуль `github` SHALL отвечать за взаимодействие с GitHub API: получение данных Issue, публикацию ветки и создание Pull Request, и НЕ должен выполнять локальные Git-операции.

#### Scenario: Операции GitHub API отделены от локальных

- **WHEN** требуется публикация ветки или создание PR
- **THEN** это выполняется модулем `github`, а не модулем `workspace`

### Requirement: Модуль web является интерфейсом без бизнес-правил

Модуль `web` SHALL предоставлять API и интерфейс для запуска workflow, просмотра состояния и взаимодействия с пользователем, и НЕ должен управлять последовательностью этапов, запускать Pi напрямую или содержать бизнес-правила workflow.

#### Scenario: Web не содержит бизнес-логики

- **WHEN** web обрабатывает запрос запуска процесса
- **THEN** он передаёт управление бизнес-модулю `workflow` и не реализует логику этапов самостоятельно

### Requirement: Бизнес-логика отделена от инфраструктурных деталей

Бизнес-логика SHALL принадлежать соответствующему доменному модулю, а инфраструктурные интеграции (Temporal, Pi, Git, GitHub) НЕ должны определять бизнес-модель.

#### Scenario: Инфраструктура за публичным контрактом

- **WHEN** доменный модуль использует внешнюю систему
- **THEN** доступ осуществляется через явный публичный контракт, без прямой зависимости бизнес-модели от реализации интеграции

### Requirement: Модули взаимодействуют только через публичные контракты

Внутренности модуля SHALL быть недоступны другим модулям напрямую; взаимодействие SHALL происходить только через явно определённые публичные контракты.

#### Scenario: Изоляция внутренностей

- **WHEN** один модуль обращается к другому
- **THEN** обращение идёт через публичный контракт, а внутренние классы модуля остаются инкапсулированными

### Requirement: Циклические зависимости между модулями запрещены

Зависимости между модулями SHALL быть ацикличными; циклические зависимости запрещены.

#### Scenario: Проверка ацикличности

- **WHEN** анализируется граф зависимостей модулей
- **THEN** в нём отсутствуют циклы

### Requirement: Произвольный общий модуль не вводится

Отдельный общий модуль (например, `shared` или `common`) SHALL вводиться только при конкретной обоснованной необходимости, а не по умолчанию; отдельный модуль `artifacts` не вводится, пока не выделена самостоятельная бизнес-функция управления артефактами.

#### Scenario: Отсутствие преждевременной абстракции

- **WHEN** рассматривается добавление общего или `artifacts` модуля
- **THEN** он не создаётся без самостоятельной обоснованной бизнес-функции

### Requirement: Границы модулей проверяемы средствами Spring Modulith

Архитектура SHALL допускать автоматическую проверку границ модулей, запрета доступа к внутренностям и отсутствия циклов средствами Spring Modulith.

#### Scenario: Автоматическая проверка

- **WHEN** выполняется архитектурная проверка Spring Modulith
- **THEN** нарушения границ модулей, циклов или доступа к внутренностям обнаруживаются автоматически
