# Proposal

## Why

`AlwaysPassVerifier` (confirmed by reading `src/main/java/.../workflow/infrastructure/AlwaysPassVerifier.java`) is a placeholder that returns `true` unconditionally for every workflow, regardless of the target repository's actual state; the `Verifier` port it implements returns only a `boolean`, so `WorkflowEngineImpl.advance()`'s `VERIFICATION` case cannot distinguish "the implementation was actually checked and passed" from "no check exists, so it trivially passed" from "a check exists but could not run." This means `VERIFICATION` currently guarantees nothing about the implementation's correctness and silently always lets the workflow proceed to `REVIEW`. There is also no project-agnostic way to configure what "verification" means for a given target repository (no assumption about build tooling exists anywhere in the codebase, confirmed by grep), and no mechanism to run an external command with bounded argv/cwd/timeout and capture bounded output.

Separately, a configuration mechanism based on Spring's `@ConfigurationProperties` is bound once at JVM startup: changing `pi-flow.verification.*` in `application.yaml` has no effect until the process restarts. A `NOT_CONFIGURED` recovery path that requires a process restart to take effect is not a recovery path a user can act on from within a running workflow - a workflow paused waiting for verification configuration needs the operator to be able to add or fix that configuration and retry *within the same running process*, not restart the whole application and lose every other in-flight workflow held in the in-memory `WorkflowRepository`.

## Depends on

This change requires plan 10 (`10-enforce-workflow-transition-guards`), plan 11 (`11-harden-pi-result-contract`), and plan 12 (`12-add-stage-context-and-review-verdicts`) to be fully implemented first. This change's design and tasks assume `Workflow`'s terminal-immutability guard (plan 10), the hardened `PiRunResult` contract (plan 11), and plan 12's extended `StageOutcome` shape (`Optional<ReviewVerdict> verdict`, `Optional<List<String>> findings`) already exist in `src/main/java`. This change extends that already-landed `StageOutcome` shape directly; it does not re-derive, duplicate, or provide a fallback implementation of any part of plans 10-12, and it does not add a conditional "if plan 12 isn't implemented yet, extend `StageOutcome` from its original shape instead" path. If plan 10, 11, or 12 is not yet implemented when this change is picked up for implementation, implementation of this change SHALL NOT start until all three are.

## What Changes

- **BREAKING**: Replace the `Verifier` port's `boolean verify(Workflow)` contract with a richer `VerificationResult` carrying one of four outcomes: `PASSED`, `FAILED`, `NOT_CONFIGURED`, or `INFRASTRUCTURE_ERROR`, plus a bounded diagnostic report (command output, exit code, and whether the report was truncated).
- Add a configurable deterministic check mechanism read from a per-target-repository configuration file, not from startup-bound Spring properties: for a given target repository, the orchestrator SHALL look for a verification configuration file at a configurable path (default: a fixed relative path inside the target repository, e.g. `.pi-flow/verify.json`, overridable via `pi-flow.verification.config-path`) and SHALL read that file **fresh on every verification attempt** (including every retry), so a user can create, edit, or fix that file while the application keeps running and have the very next verification attempt observe the change without any restart. The file's schema is fixed and explicit: a JSON object with `command` (a non-empty array of strings, the argument vector), `timeoutSeconds` (a positive integer), and an optional `workingDirectory` (a string; defaults to the target repository root when absent). No other shape is accepted. The orchestrator SHALL NOT execute any command supplied by an agent/model; the only command ever executed is the one read from this user-authored, user-controlled file.
- Replace `AlwaysPassVerifier` with a new `Verifier` implementation (name decided in design.md) that, on every `verify(Workflow)` call: re-reads the configuration file for the workflow's target repository; if the file is absent, reports `NOT_CONFIGURED`; if the file is present but malformed, unreadable, or fails schema validation, reports `INFRASTRUCTURE_ERROR` (distinct from `NOT_CONFIGURED` - the user has started configuring verification but the configuration itself is broken, which is a different, more specific thing to fix than "nothing is configured yet"); if the file is present and valid, runs the configured command and reports `PASSED` (exit code 0 within timeout), `FAILED` (the command ran to completion but exited nonzero, or ran past its timeout and was terminated), or `INFRASTRUCTURE_ERROR` (the command could not be started at all - executable not found, permission denied, configured working directory does not exist). `FAILED` and `INFRASTRUCTURE_ERROR` SHALL be kept distinguishable in the result and its report text: `FAILED` means the configured check actually ran and reported a problem; `INFRASTRUCTURE_ERROR` means the check could not be meaningfully run at all.
- `WorkflowEngineImpl.advance()`'s `VERIFICATION` case SHALL route `PASSED` to `REVIEW` (as today's `true` case does) and `FAILED` to `IMPLEMENTATION` (as today's `false` case does, i.e. the existing correction loop). `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` SHALL NOT be routed as either `PASSED` or `FAILED`: both SHALL block automatic progression to `REVIEW` or `ACCEPTANCE` and leave the workflow in an explicit, inspectable, non-terminal, `AWAITING_USER` state at the `VERIFICATION` stage that names the specific cause (missing configuration file vs. a specific infrastructure problem), recoverable by a `retryStage` action once the user has fixed the underlying cause - in the same running application process, with no restart required, because the configuration file is re-read fresh on every attempt (see "Depends on" and design.md for how this reconciles with plan 10's terminal-immutability guarantee, and the generalization boundary with plan 15).
- Verification reports SHALL be bounded: a configurable maximum size truncates captured command output, and the result explicitly flags when truncation occurred, so a pathological command cannot produce an unbounded report.
- Add unit and fixture-based tests covering: a passing command, a failing command (nonzero exit), a timing-out command, no configuration file present, a malformed configuration file, a configuration file naming a nonexistent executable, a configuration file naming a nonexistent working directory, a report exceeding the configured bound being truncated with the truncation flag set, and the configuration file being re-read (and a changed command taking effect) across two successive verification attempts within the same running process with no restart in between.

## Capabilities

### New Capabilities
- `deterministic-verification`: defines the per-target-repository, freshly-re-read-on-every-attempt configuration file for the external-command verification check (schema, argv, working directory, timeout), its four-valued `PASSED`/`FAILED`/`NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` result, the distinction between a command failure and an infrastructure error, bounded/truncatable reports, and the explicit, same-process-recoverable behavior required when verification cannot run as configured (or is not configured at all).

### Modified Capabilities
- `workflow-orchestration`: the "Correction loop" requirement's verification-failure routing is restated against the four-valued `VerificationResult` instead of a boolean, and new routing rules for `NOT_CONFIGURED` and `INFRASTRUCTURE_ERROR` are added so neither is silently treated as a pass or a content-correction failure.

## Impact

- `src/main/java/.../workflow/application/Verifier.java`: port signature changes from `boolean verify(Workflow)` to a method returning `VerificationResult`. **BREAKING**.
- `src/main/java/.../workflow/infrastructure/AlwaysPassVerifier.java`: removed/replaced by a command-running `Verifier` implementation that reads its configuration from a per-target-repository file on every invocation.
- New `VerificationResult` type (status + report + truncation flag), new `VerificationStatus` enum (`PASSED`, `FAILED`, `NOT_CONFIGURED`, `INFRASTRUCTURE_ERROR`) extending plan 12's already-landed `StageOutcome` shape - package placement decided in design.md.
- New `pi-flow.verification.config-path` property (the only startup-bound setting this change introduces; it configures *where to look*, not *what to run*) bound via `@ConfigurationProperties`, following the existing `AgentProperties`/`PiProperties` pattern. The command/timeout/working-directory configuration itself is read fresh from the per-target-repository file on every attempt, never from Spring-bound properties.
- `src/main/java/.../workflow/application/WorkflowEngineImpl.java`: `VERIFICATION` case in `advance()` routes on the four-valued result instead of a boolean; `NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` handling added per design.md, pausing the workflow at `AWAITING_USER` with a `retryStage`-compatible recovery contract.
- Tests: new tests for the command-running verifier (passing/failing/timeout/not-configured/malformed-config/missing-executable/missing-working-directory/truncated-report/live-reconfiguration cases); `WorkflowEngineImplTest` gains cases for `NOT_CONFIGURED`/`INFRASTRUCTURE_ERROR` routing; any existing test currently depending on `AlwaysPassVerifier`'s always-pass behavior is updated to use an explicit test double returning `PASSED`.
- No changes to `agent-invocation` capability or `StageRunner`/`AgentStageRunner`; this change is scoped to the `VERIFICATION` stage's `Verifier` port only.
- Plan 14 (exact-change binding) and plan 15 (controlled stage retry, generalizing the recovery action this change introduces into a single cross-stage `retryStage` mechanism) build on this change's `VerificationResult`/pause-state shape but are not implemented here. This change defines the recovery contract precisely enough (bounded, user-initiated, same-process, re-read-on-retry) that plan 15 can generalize it without redesigning it.
