# Proposal

## Why

`WorkflowEngineImpl`/`JsonModePiRunner` log individual events today (`log.info`/`log.warn` per Pi run, per stage dispatch), but there is no structured, bounded record of a workflow's attempt history: `Workflow.outcomes()` is the only inspectable record, and it carries no duration, no machine-readable failure category, and no link back to the raw log lines that explain *why* a given attempt failed (confirmed by reading `WorkflowEngineImpl.advance()`, `Workflow`, `StageOutcome`, and `JsonModePiRunner.runCommand`). A user watching a workflow retry (plan 15) or fail has to scroll raw SLF4J log output and manually correlate timestamps to stage names to understand what happened.

Today's logging is also actively unsafe: `JsonModePiRunner.runCommand` logs, at `INFO`, the full child-process `command` list (which embeds the raw agent prompt as its last argument) on every Pi run start, and logs `finalText` (truncated only for display, not redacted) and `diagnostics` on every Pi run finish - confirmed by reading `JsonModePiRunner.runCommand`'s two `log.info` call sites. Any new diagnostics surface must not add a second way to leak the same data, and this change is also the place to remove the existing leak, since it is the first change to define what a "safe" stage-attempt record looks like.

This change depends on plans 10 through 15 for the shapes it reports on: plan 10 (terminal-state immutability and gate-command conventions), plan 11 (`PiRunResult`/diagnostics hardening), plan 12 (`ReviewVerdict`), plan 13 (`VerificationResult`/`NOT_CONFIGURED`), 14 (approval binding), and 15 (`AttemptKind`, technical-retry vs. content-correction classification, `retryStage`, and the per-stage/per-workflow attempt history plan 15 already builds). As of this writing, none of plans 10-15 are implemented in `src/main/java` (confirmed by reading `StageOutcome` - still the original 3-field `(stage, success, output)` record - `WorkflowEngineImpl.advance()` - still the undifferentiated `MAX_ADVANCE_STEPS` loop guard - and the absence of `AttemptKind`, `RetryProperties`, `ReviewVerdict`, `VerificationResult`, or `VerificationProperties` anywhere in `src/main/java`). This change is sequenced and planned to be implemented after plans 10-15 land, in numeric order; it is not designed to work against a hypothetical "whichever of 10-15 happens to exist" runtime state. Plan 15 in particular is being actively updated concurrently with this change; this proposal and its sibling artifacts are written against plan 15's latest `controlled-stage-retry`/`workflow-orchestration` spec deltas and design decisions as currently committed to disk, re-read at the time this change is implemented.

## What Changes

- Add an in-memory, per-workflow diagnostics record that accumulates one **diagnostic entry** per stage attempt (initial attempt, technical retry, or content-correction loop iteration). Attempt identity (stage, attempt sequence number, `AttemptKind`) SHALL be read from plan 15's `Workflow`/`StageOutcome` attempt-history fields - this change SHALL NOT introduce its own, independent attempt counter or a second attempt-sequencing scheme. Each diagnostic entry SHALL carry: the workflow id, the stage, the attempt sequence number (sourced from plan 15), a start timestamp, a duration, a **category** (a closed, machine-readable classification: `SUCCESS`, `TECHNICAL_FAILURE`, `CONTENT_CORRECTION`, `TIMEOUT`, `NOT_CONFIGURED`, mapped from plan 12's `ReviewVerdict`, plan 13's `VerificationResult`, and plan 15's `AttemptKind`), and a short, bounded **reason** string.
- Preserve two distinct records with an explicit, documented relationship instead of one undifferentiated history: plan 15's `Workflow.outcomes()` remains the full, unbounded, append-only attempt history (the system of record for "what happened and in what order," never truncated or dropped by this change) and this change's `WorkflowDiagnostics` is a derived, bounded, truncatable *reporting* projection built from that history for display and logging. This change SHALL NOT replace, shrink, or alter `Workflow.outcomes()`'s retention; it SHALL NOT be used as a substitute source of truth for attempt history, budget enforcement, or retry eligibility, all of which remain plan 15's responsibility.
- The reason string SHALL be built only from safe, already-process/protocol-scoped fields: stage name, outcome category, exit/status codes, and existing diagnostic text that is itself already scoped to process/protocol metadata (e.g. `PiRunResult.diagnostics()`'s timeout/process-start/malformed-protocol text per plan 11). The reason string SHALL NOT include agent prompt text, agent response/final text, or any other raw provider output; no formatting of a diagnostic entry SHALL concatenate `finalText`, a prompt, or an equivalent field into the recorded reason.
- Remove the existing prompt/argv/final-text leakage at its source: `JsonModePiRunner`'s `INFO`-level "Starting Pi run" log line SHALL NOT include the raw prompt or the full child-process argument list verbatim (it SHALL log only the executable name/stage-identifying context and non-sensitive process parameters such as working directory and timeout), and its "Pi run finished" log line SHALL NOT include `finalText` in any form (truncated or not) - it SHALL log only status, exit code, and the already-safe `diagnostics` field. This is a required correction to existing, currently-shipped logging behavior, not an optional cleanup.
- Diagnostic entries SHALL be logged at `INFO` level through the project's existing SLF4J/Logback setup, in addition to being retained in memory; no new logging framework or sink is introduced.
- Diagnostic entries SHALL be held only in process memory, scoped to the lifetime of the owning `Workflow` instance; no new persistent store, external log shipper, metrics backend, or tracing/observability integration is introduced by this change.
- The in-memory diagnostics buffer SHALL be bounded on two independent axes - the number of entries retained per workflow, and the length of each entry's reason string - each capped at configurable, defaulted limits (following the project's `@ConfigurationProperties` pattern); the record SHALL expose whether older entries were dropped once the per-workflow entry cap is exceeded.
- Raw process output capture feeding this diagnostics surface SHALL itself be bounded and non-blocking: the stdout/stderr draining this change reports on SHALL continue to run on the existing non-blocking daemon reader threads (`JsonModePiRunner`'s existing pattern), and any text this change pulls from that capture into a reason or report SHALL be subject to the same reason-length cap - this change SHALL NOT introduce a blocking read, a synchronous full-buffer join, or an unbounded accumulation of raw process output as a side effect of building a diagnostic entry.
- Add a new shell command exposing a workflow's diagnostic history as rendered text (stage, attempt, duration, category, reason, per entry, in chronological order), following the existing `FlowCommands` pattern.
- Add tests covering: an entry recorded per attempt with correct stage/attempt/duration/category sourced from plan 15's attempt history (not a duplicate counter); a technical failure and a content-correction attempt producing distinguishable categories; the reason string never containing a known prompt/response fixture value; `JsonModePiRunner`'s log lines no longer containing a known fixture prompt or final-text value; the per-workflow entry cap enforced with the dropped-entries flag set once exceeded; the reason-length cap enforced per entry; and the new shell command rendering a known diagnostics record as text. Tests SHALL use safe, non-secret fixture values by default and SHALL NOT assert on or require any real credential, API key, or other secret appearing in a log or report.

## Capabilities

### New Capabilities
- `workflow-diagnostics`: defines the per-workflow, in-memory, bounded diagnostic entry record (stage, attempt, duration, category, reason) sourced from plan 15's attempt history, its safe-content exclusion of prompt/provider output and secrets, its `INFO`-level logging, the shell command that renders it, and the required removal of the existing argv/prompt/final-text log leakage in `JsonModePiRunner`.

### Modified Capabilities
- `agent-invocation`: `JsonModePiRunner`'s "Starting Pi run"/"Pi run finished" log lines are corrected to stop logging the raw prompt, full argv, and `finalText`; no change to `PiRunner`/`PiRunResult`'s public shape or to any routing/transition logic in `WorkflowEngineImpl.advance()`.

## Impact

- New type(s) for the diagnostic entry and the bounded per-workflow diagnostics record, in a new `workflow/diagnostics` sub-package.
- `src/main/java/.../workflow/domain/Workflow.java` or `src/main/java/.../workflow/application/WorkflowEngineImpl.java`: gains the call site(s) that record a diagnostic entry at each attempt boundary, reading attempt identity from plan 15's `Workflow`/`StageOutcome` fields rather than tracking a parallel counter.
- `src/main/java/.../agent/infrastructure/JsonModePiRunner.java`: its two `log.info` call sites in `runCommand` are corrected to drop the raw prompt/argv and `finalText`.
- New configuration properties (e.g. `pi-flow.diagnostics.*`) bound via `@ConfigurationProperties`, following the existing `AgentProperties`/`PiProperties` pattern, for the per-workflow entry cap and the per-entry reason-length cap, each with a stated default.
- `src/main/java/.../shell/FlowCommands.java` (or a new diagnostics-focused command class in `shell/`): gains a new command rendering a workflow's diagnostic history as text.
- Tests: new unit tests for the diagnostic entry/record types, the new shell command, and the corrected `JsonModePiRunner` log output; no change to existing `WorkflowEngineImplTest`/`WorkflowTest` assertions beyond what is needed to observe the new recording call sites.
- Requires plans 10-15 to be implemented first, in that numeric order, and consumed as implemented (not planned-only) shapes: this change reads plan 15's actual `Workflow`/`StageOutcome` attempt-history fields and plan 12/13's actual `ReviewVerdict`/`VerificationResult` fields as they exist in `src/main/java` at the time this change is implemented. If plan 15 has changed since this proposal was written (it is being updated concurrently), this change's design.md and tasks.md are re-aligned against plan 15's latest committed artifacts before implementation begins, rather than against a snapshot taken when this proposal was drafted. This change does NOT define a speculative, independent fallback behavior for the case where 10-15 are not yet implemented; it has no supported standalone mode and SHALL NOT be implemented ahead of its predecessors.
- No new external dependency (no logging framework change, no metrics/tracing library, no persistent store); this change is additive and entirely local to the running JVM process, aside from the required correction to `JsonModePiRunner`'s existing log lines.
