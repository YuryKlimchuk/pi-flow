# Proposal

## Why

pi-flow — локальный оркестратор AI-агентов для автоматизации разработки ПО. Бизнес-процесс описан в существующей capability `development-workflow`, но в проекте нет зафиксированной базовой модульной архитектуры: не определены состав модулей, их границы ответственности, направления зависимостей и правила взаимодействия. Без этого фундамента последующая реализация workflow, интеграции Temporal/Pi/Git/GitHub и web-слоя будет фрагментарной, а границы модульности не удастся автоматически проверять средствами Spring Modulith.

## What Changes

1. Определяется базовая модульная архитектура `pi-flow` (модульный монолит на Spring Modulith):
   - состав и назначение модулей;
   - границы ответственности каждого модуля;
   - правила взаимодействия между модулями и направление зависимостей;
   - размещение бизнес-логики и инфраструктурных интеграций;
   - архитектурные ограничения для сохранения модульности.
2. Формируется отдельный документ ответственности модулей (`docs/architecture/module-responsibilities.md`), по которому можно определить, куда относится новая функциональность.
3. Архитектурные требования формулируются так, чтобы их можно было автоматически проверять средствами Spring Modulith (запрет циклов, запрет доступа к внутренностям модулей, контроль направления зависимостей).

Реализация бизнес-функциональности, запуск Pi-агентов и рабочая реализация workflow в это изменение НЕ входят.

## Capabilities

### New Capabilities

- `modular-architecture`: базовая модульная архитектура приложения — состав модулей, их границы ответственности, допустимые и запрещённые взаимодействия, направление зависимостей и ограничения модульности, пригодные для автоматической проверки.

### Modified Capabilities

<!-- нет — `development-workflow` не меняется, только получает архитектурный фундамент -->

## Impact

1. **Архитектура**: вводится перечень модулей и правила их взаимодействия (фундамент, не реализация).
2. **Документация**: новый файл `docs/architecture/module-responsibilities.md`.
3. **Проверяемость**: впоследствии — архитектурные тесты Spring Modulith (в это изменение входят только описания требований, не сами тесты/код).
4. **Существующая spec** `development-workflow` не изменяется — она остаётся основой бизнес-процесса, поверх которого строится модульность.
